# ZoomChartComponent

Этот компонент написан полностью ИИ потому что тут много математики над которой мне было лень думать.

Компонент для `InteractionController`, управляющий областью отображения графика (`chart.setRenderBounds`):
пан мышью/тачем, зум колесом, пинч-зум, инерция и лимиты с опциональным «резиновым» оверскроллом (elastic).
Шаговое колесо получает короткую анимацию зума; уже плавный ввод применяется напрямую.
Неоднозначное начало жеста ждёт классификации до 40 мс.
При одноосевом пане/зуме дополнительно плавно анимирует авто-подгоняемую противоположную ось.
Опционально синхронизирует окно ведущей оси с другими графиками (`boundsSync`, см. ниже).
Сам ничего не рисует. Функционал завершён — это финальное состояние, не закладывайте сюда архитектуру «на будущее».

## Использование

```ts
new ZoomChartComponent({
  chart,                       // UniversalChart
  zoom: true,                  // разрешить зум (колесо + пинч)
  panDirection: 'horizontal',  // 'horizontal' | 'vertical' | 'all' | false — какие оси активны
  deceleration: { mousePan: 0.99, touchPan: 0.99, touchZoom: 0.95 }, // опционально; значение вне (0,1) отключает инерцию
  boundsSync,                  // опционально; общий BoundsSynchronizer для связки графиков (см. ниже)
  limits: { minX, maxX, minDeltaX, maxDeltaX, /* ...Y */, elastic: true }, // опционально
})
```

Единственное место использования в проекте: `src/pages/infographics/pages/onslaught/leaderboard/components/detail/Charts.ts`.

## Анализ колёсика

`chart/wheelInput.ts` — единый для библиотеки наблюдатель, подключённый при загрузке `BaseChart`.
Он слушает `window` в capture-фазе с `passive: true`, включая события вне графиков и события,
которые график затем останавливает. Ничего не отменяет и не меняет прокрутку страницы.
Наблюдатель живёт до выгрузки страницы (при HMR старый listener снимается), поэтому профиль
сохраняется между графиками и периодами без смонтированных графиков. До загрузки библиотеки
события не собираются. Профиль не сохраняется в localStorage и не является идентификатором мыши.

Собственная эвристика анализирует поток событий, а не модель устройства. Строки/страницы
считаются шаговым вводом, пиксельные дельты не больше 3 — уже плавным. Неоднозначное начало
наблюдается до 40 мс: небольшие меняющиеся дельты (до 32 px) с интервалом до 20 мс
дают плавный режим; одинаковые шаги и кратные им значения этого не доказывают.
При отсутствии признаков плавности выбирается шаговый режим. Крупные дельты с одинаковым временем сами
по себе не доказывают плавность. Выбранный режим удерживается до паузы больше 400 мс;
явно мелкий ввод или смена единиц могут переключить его раньше.
Это эвристика без гарантии распознавания: например, гладкий поток строго одинаковых дельт
больше 3 px может выглядеть как шаги. Никаких специальных чисел для конкретных драйверов нет.
`Ctrl+wheel` и нативный `momentum` идут напрямую и не заменяют выученный профиль.
Последний профиль, причина решения, дельты, интервал и сброс доступны на debug-стенде.

`WheelZoom` скрывает от `ZoomChartComponent` классификацию, ожидание первого события,
очередь и анимацию. Его интерфейс: `push(...)` записывает ввод и возвращает, принят ли он; `flush(now, apply, constrain)`
выдаёт готовые приращения масштаба и сообщает, нужны ли ещё кадры; `cancelAnimation()`
отменяет хвост при начале пана мышью. `apply` синхронно применяет приращение к текущим raw-границам,
а `constrain` ограничивает оставшийся путь к цели. Геометрия курсора, hard/elastic-лимиты
и release остаются ответственностью графика. Общий анализатор возвращает решение по ссылке,
поэтому задержанная первая дельта применяется ровно один раз, даже если следующее событие
пришло вне графика. При отмене жеста весь `WheelZoom` просто отбрасывается; собственных таймеров
и подписок у него нет.

Нулевая, нечисловая или чисто горизонтальная дельта не создаёт wheel-жест, не меняет время
последнего зума и не перехватывает bounds-sync/инерцию. Общий анализатор пропускает пустые
события, поэтому их нельзя ставить в очередь с его начальным `unknown`: такое решение
не будет разрешено последующим жестом и заблокирует и зум, и release после пана.

Для сглаживания используется уже существующий `CriticalFollower`, как для auto-fit оси.
В логарифмическом масштабе он непрерывно догоняет общую цель, не перезапуская анимацию на каждом
шаге. Скорость сохраняется при обновлении цели; при развороте скорость в неверную сторону
сбрасывается. Остановка определяется остатком в пикселях и скоростью, а не фиксированным таймером.
Плавный ввод применяет накопленную цель сразу; нативный пинч/momentum начинает от текущего окна.
Hard-лимиты ограничивают и цель, чтобы невидимый остаток за пределом не поглощал обратное
вращение; elastic по-прежнему допускает overzoom с последующей пружиной возврата.
Чувствительность сохранена: строки ×16, страницы ×высота, пиксели ×1;
log-delta = delta ×0.001 с ограничением ±0.5 на событие.
Каждое приращение проходит обычную raw → displayed проекцию и bounds-sync.

Тач-пан и пинч отменяют wheel-хвост и работают прежним путём, со своей прежней инерцией и лимитами.
Внешняя установка границ через `onSetRenderBounds` отменяет wheel-хвост, чтобы он не перезаписывал
выбранную область своим следующим кадром.

## Модель

- **Обработчики движения записывают состояние** (`pan` / `pinch` / `wheel`).
  Всё применяется одним пайплайном `applyInteraction`: pinch → pan → wheel → шаг моушенов → проекция → `setRenderBounds`.
  Обычно его вызывает `onBeforeLayout`; `onPanEnd` также вызывает его синхронно, чтобы последнее смещение
  и release были обработаны до возможного клика. При отсутствии оставшегося ввода и моушенов
  подстройка auto-fit оси сразу отпускается, поэтому данные, изменённые кликом, не наследуют её анимацию.
- **Отмена инерции из клика.** Обработчик вызывает `event.preventPanInertion()`;
  после всех обработчиков `onAfterClick` отменяет инерцию пана. Инерция зума и пружины
  сохраняются; если отменённая инерция оставила окно за лимитом, запускается пружина возврата.
  При отсутствии остальных движений auto-fit ось сразу отпускается.
- **Raw vs displayed.** Жесты и инерция интегрируются в «raw» (несопротивляющемся) пространстве.
  Отображаемые границы — чистая проекция raw: тождественная внутри лимитов, rubber band снаружи (elastic)
  или clamp (hard). В hard-режиме raw наоборот жёстко клампится на каждом шаге применения.
- **Якорь проекции (anchorT)** — экранная доля, вокруг которой растягивается эластичный overzoom:
  середина пинча / курсор колеса во время зума, иначе 0.5. При смене якоря raw пересчитывается
  (`rebaseRawAnchor`), чтобы displayed не прыгнул.
- **Каналы.** Каждая ось анимируется двумя независимыми каналами: `center` (перенос) и `logRange` (зум).
  Поэтому, например, пружина возврата зума продолжает работать, пока по той же оси летит инерция пана.
- **Моушены.** Канал владеет либо инерцией (интегрирует raw напрямую), либо пружиной (следует кривой
  в displayed-пространстве, записывается обратно в raw через обратную проекцию). Пружина стартует только
  когда ввод, владеющий каналом, закончился.
- **Release** (`releaseAxis` → `decideChannelRelease`): если канал внутри лимитов или скорости хватит
  доскользить внутрь — инерция; иначе пружина к ближайшей валидной цели, со скоростью, переведённой
  в displayed через производную rubber band. `velocity: null` для канала = не трогать его текущий моушен;
  `inertia: null` = разрешены только пружины.
- **Инерция у границы**: пересекая лимит наружу, передаёт остаток скорости пружине, прижатой к границе
  (`inertiaBounceMotion`) — отскок. Во время активного жеста инерция не может оверскроллить (жёсткая остановка).
- **Авто-подгонка противоположной оси** (`stepAutoFollow`). При `panDirection: 'horizontal' | 'vertical'`
  вторую ось (`autoFitAxis`) компонент не двигает — она авто-подгоняется под данные. Чтобы её экстент не
  «прыгал» на каждом кадре пана, компонент сам ведёт её `CriticalFollower`'ом (min и max независимо) к
  целевому фиту (`chart.autoFitBounds(drivenConstraint)`) и пишет в тот же `setRenderBounds`-патч. Догнав фит
  и когда ввод закончился — «отпускает» ось (`setRenderBounds({ minY: null, maxY: null })`), возвращая её
  синхронной авто-подгонке. Анимацию запускает только ввод: изменение данных вне взаимодействия идёт штатным
  синхронным путём (`autoFollow === null`).
- **Синхронизация между графиками** (`boundsSync: BoundsSynchronizer`, хаб в `../../sync/`). Связка графиков
  делит окно синкаемых осей (направление как у `panDirection`: `new BoundsSynchronizer('horizontal')`). Компонент — и **паблишер**, и **консьюмер**: чарт, по которому
  водят локально, становится источником (`claim` в `onPanBegin`/`onTouchZoomBegin`/`onWheelZoom`) и каждый кадр
  публикует окно ведущей оси + фазу (`active`/`end`). Ведомый инжектит окно в свой `patch` и **сам** гоняет
  `stepAutoFollow` для своей auto-fit оси (`followExternalBounds`). **`active`-кадр ведомый применяет синхронно
  в `onExternalPublish`** — в кадре *источника*, до рендера своего hover'а (лок-степ, см. «Неочевидные места»);
  осадочный `end`-хвост доезжает локально в `onBeforeLayout`. Арбитраж по токену-источнику (`this`): `consume`
  возвращает `null` источнику (отсечка self-echo) и уступает локальному активному вводу; входящий `active` гасит
  собственную инерцию ведомого. Подписка на хаб живёт в `attach`/`detach` (+ `resign` при размонтировании).
  Без `boundsSync` — поведение идентично, все ветки no-op.

## Неочевидные места (не «чинить»)

- `wheel` — это батч: события копятся внутри `WheelZoom`, применяются в следующем `onBeforeLayout` напрямую
  или задают цель анимации. `deltaMode` нормализуется в пиксельный масштаб, log-delta ограничивается
  для каждого события до записи в батч; множитель зума считается экспонентой, поэтому большие
  отрицательные дельты не отбрасываются. Батч живёт до завершения анимации, а при elastic-лимитах —
  ещё и до `WHEEL_BATCH_TIMEOUT` после последнего события, чтобы затем стартовала пружина возврата.
  Пинч всегда убивает wheel-батч.
- Сэмплеры скорости (`recordPanVelocity`, `samplePinchVelocity`) отбрасывают «bursts» — события,
  пришедшие сильно чаще среднего темпа: такие сэмплы накапливаются в следующий (baseline не сдвигается).
  Пауза дольше `INPUT_STOP_TIMEOUT` обнуляет скорость (палец остановился перед отпусканием).
- Пан сразу после пинча подавляет собственную инерцию (`suppressInertia`), пока не сдвинется на
  `PAN_SUPPRESS_RELEASE_DISTANCE` px — иначе дрожание пальцев при отрыве убивало бы инерцию пинча.
- Политики остановки моушенов различаются по вводу: `stopAllMotions` (пинч), `stopMotionsForPan`
  (тач-пан сохраняет зум-инерцию и пружину возврата зума), `stopMotionsForWheel` (сохраняет инерцию пана).
- В лимитах все сравнения с fp-допуском `LIMITS_EPSILON`: bounds постоянно раскладываются в
  (center, range) и собираются обратно, дрейф в несколько ULP не должен считаться нарушением.
- `clampAxisToLimits` возвращает входной объект без изменений, если ничего не нарушено — вызывающие
  сравнивают результат с входом по ссылке/значению, чтобы отличить реальный clamp.
- `null` в `setRenderBounds` = отпустить ось обратно в авто-подгонку; `undefined` = не трогать; число = зафиксировать.
  `CriticalFollower` стартует от текущих `space.bounds` (без скачка) и живёт после отпускания ввода, пока не осядет,
  поэтому `onBeforeLayout` не выходит рано, пока `autoFollow !== null`.
- **Bounds-sync идёт ЧЕРЕЗ компонент, а не в обход.** Наивный `otherChart.setRenderBounds({minX,maxX})` даёт
  снап auto-fit оси (Y) на ведомом: её аниматор (`stepAutoFollow`) живёт здесь и заводится только от «ввода», а
  прямой пин X пересчитает Y синхронным `autoFitBounds` мгновенно. Поэтому `followExternalBounds` кладёт внешнее
  окно X в свой `patch` и гоняет **свой** `stepAutoFollow` (тот же `omega`), помечая кадр `active`-фазой как
  «busy» — Y ведомого анимируется так же, как у ведущего. Синкается только ведущая ось; auto-fit ось всегда локальна.
- **Лок-степ ведомого (иначе hover дребезжит).** У одиночного графика bounds ставятся синхронно в `onBeforeLayout`
  (`setRenderBounds(patch, true)` → немедленный `relayout`), поэтому hover в поздних шагах рендера читает уже
  свежие bounds и маркер/тултип «приклеен» к точке данных. У ведомого нельзя ждать его собственного кадра: порядок
  хендлеров чартов в батче рендер-менеджера недетерминирован, ведомый читал бы bounds источника с лагом в кадр —
  hover дребезжит. Поэтому `active`-окно применяется **синхронно в кадре источника** (`onExternalPublish`, дёргается
  из `publish`→`notify`), до рендера hover'а ведомого. Его собственный `onBeforeLayout` в `active`-фазе только
  держит цикл рендера; шаг Y идёт по dt, так что повторный вызов в тот же кадр — почти no-op. `relayout` не зовёт
  `beforeLayout` (нет реэнтранси), а step-1 `relayout` ведомого попадает в `layoutCacheKey` (push уже посчитал).
