# Слой данных: ClickHouse

Фронтенд ходит **напрямую в ClickHouse** через web-прокси. Это центральный механизм всего сайта.

## Клиент (`src/db/client.ts`)

`createDatabase` создаёт клиент и обычный `query`, локальный кеш и реестр выполняющихся
запросов. Этот модуль не импортирует Vue, `location` или `localStorage` и используется
как браузером, так и Bun. Адрес передаётся целиком, включая путь прокси.

Браузерный экземпляр создаётся один раз в `src/db/index.ts`:

```ts
const database = createDatabase({
  url: new URL('/api/db/', CLICKHOUSE_WEB_PROXY_URL).href,
  username: 'public',
}, response => { /* обновление счётчиков в localStorage */ })
```

`src/db/index.ts` сохраняет публичные импорты `query`, `queryComputed`, `queryAsync`
и остальные Vue-хелперы. Браузерные контексты используют этот же `query`, экземпляр
клиента и локальный кеш. В Bun создаётся свой экземпляр с серверными настройками;
отдельной реализации запросов для контекстов нет. Callback статистики вызывается
только при получении ответа из сети, без повторного учёта локальных HIT и дубликатов.

- Пользователь `public` — только чтение. CORS-заголовок включён настройкой `add_http_cors_header`. В dev запросы также идут напрямую на сервер из `VITE_DEFAULT_URL_PREFIX`, без Vite proxy. Три заголовка кеша должны быть явно разрешены в CORS сервера.
- Общий HTTP-кеш использует группу (`scope`) `public` для `public` и `internal-public`.
  Клиент задаёт группу явно и не читает Authorization при построении ключа.
  Nginx и Worker определяют группу по имени пользователя. HIT публичен и доступен
  даже с неверным паролем; другие пользователи обходят общий кеш. Хеш включает
  SQL, параметры, группу и политику кеша. Авторизация и адрес endpoint не входят в хеш.
  Исходная авторизация сохраняется для MISS. `proxyCache` включается явно.
- Сборка meta-renderer получает `VITE_META_RENDERER=true` из Vite-конфига и использует
  `/api/db/` своего локального origin. Bun добавляет пароль `internal-public` и передаёт
  запрос во внутренний Nginx. Основной SPA и Meta Studio продолжают использовать `public`.
- В браузере `keep_alive.enabled = false`: Fetch иначе ограничивает суммарный размер тел запросов в полёте до 64 КиБ. Несколько запросов колонок со списками дат могут превышать этот лимит. В Bun keep-alive включён для переиспользования соединений. HTTP-сжатие ответов включено.
- Счётчики статистики использования (`totalRequests`, `totalElapsed`, `totalRowsRead`, `totalBytesRead`) — в localStorage, показываются в футере/настройках.

## Статусы запроса

```ts
export const loading / success / error  // символы
export type Status = loading | success | { status: error, reason: string }
mergeStatuses(...statuses)  // error > loading > success
isErrorStatus(status)
```

Компоненты-виджеты принимают `status: Status` и сами показывают лоадер/ошибку.

## Query-хелперы (импорт из `src/db/index.ts`)

| Функция | Что делает |
| --- | --- |
| `query<T>(sql, {cache, proxyCache, allowCache, format, settings, abortSignal, concurrency, priority})` | Низкоуровневый запрос, формат JSON или JSONCompact с преобразованием строк в объекты. При `allowCache` результат кешируется локально с учётом срока политики и заголовков ответа; одинаковые запросы в полёте с той же группой, приоритетом и тем же `AbortSignal` разделяют выполнение |
| `queryComputed<T>(() => sql \| null, {cache, proxyCache, settings, enabled, allowCache, abortSignal, concurrency, priority})` | Реактивный: пересчитывается при смене SQL, политики `cache` или `enabled`; отменяет предыдущий при смене SQL, отключении или завершении Vue scope. Возвращает `ShallowRef<{status, data: T[]}>`. `null` из геттера = не выполнять |
| `queryComputedFirst<T>(..., defaultValue)` | То же, но `data` — первая строка либо дефолт |
| `queryAsync<T>(sql, {enabled, ...})` | Одноразовый запрос, ждёт `enabled === true` и выполняется один раз |
| `queryAsyncFirst<T>(sql, defaultValue, ...)` | Одноразовый + первая строка |

Обычный `query` реализован в `src/db/client.ts`; он принимает готовую `CachePolicy`.
Браузерная обёртка дополнительно разворачивает `ref` и getter политики перед вызовом.

`format` по умолчанию `JSON`; для компактного ответа можно передать `JSONCompact`.
Названия колонок передаются один раз в `meta`, строки — массивами. `query` восстанавливает
объекты, включая `totals`/`extremes`, поэтому API потребителей остаётся прежним. Формат
входит в ключ кеша и выполняющихся запросов. Реактивные хелперы поддерживают тот же параметр.
См. [формат JSONCompact](https://clickhouse.com/docs/reference/formats/JSON/JSONCompact).

`enabled` часто связывают с `useElementVisibility(cardRef)` — данные грузятся, когда карточка попала во вьюпорт.

### Ограничение параллельных запросов

Все query-хелперы, включая варианты `First`, принимают `concurrency`, `priority` и `abortSignal`. Группу создают один раз на загрузчик или общий набор виджетов и передают каждому запросу:

```ts
import { createConcurrencyGroup, query, queryComputed } from '@/db'

const concurrency = createConcurrencyGroup(2)
const controller = new AbortController()
const response = query<Row>(sql, { concurrency, abortSignal: controller.signal })
const reactiveResult = queryComputed<Row>(() => otherSql.value, { concurrency, priority: 1 })
await response
```

`src/db/concurrency.ts` запускает задачи из общей очереди, не превышая лимит: сначала с наибольшим `priority`, при равном приоритете — в порядке поступления. Приоритет по умолчанию `0`; положительные значения выполняются раньше, отрицательные — позже. Добавление приоритетного запроса не прерывает уже выполняющиеся задачи. При прямом использовании группы приоритет передаётся третьим аргументом: `concurrency.run(request, signal, priority)`.

`await query(...)` ждёт и свободного места, и полного чтения/разбора ответа. Разные группы независимы; без `concurrency` ограничений нет и `priority` не влияет на запуск. Готовый ответ из кеша возвращается без ожидания очереди; приоритет не входит в ключ кеша. Запросы с разными сигналами отмены или приоритетами не разделяют выполнение, поэтому отмена одного потребителя не прерывает другой, а приоритетный запрос не ждёт дубликат с меньшим приоритетом.

Для связанных последовательностей есть `concurrency.createOrderedGroup()`: результат
передаётся в тот же параметр `query(..., { concurrency: sourceGroup })`. Эти дочерние группы
делят лимит родителя. При равном приоритете группы упорядочены по созданию: готовое продолжение ранней группы
ставится перед ожидающими запросами поздних, внутри группы сохраняется FIFO для одного приоритета.
Уже выполняющиеся запросы не прерываются; если ранняя группа пока ждёт ответов,
свободные места занимают следующие. Приоритет учитывается раньше порядка дочерних групп.

Отмена через `AbortSignal` удаляет ожидающий запрос из очереди, а запущенному передаётся в клиент ClickHouse. Место освобождается после завершения или ошибки запроса. Реактивные хелперы также отменяют свои запросы при завершении Vue scope; `queryComputed` — при смене SQL, `null` или `enabled = false`. `queryAsync` остаётся одноразовым: после первого включения последующие изменения `enabled` не перезапускают запрос.

## Общая политика кеширования

`src/db/cache.ts` определяет `CachePolicy`, все query-хелперы принимают её через `cache`:

```ts
type CachePolicy =
  | { ttl: number }
  | { until: 'hour' | 'day' | 'month' }
  | { expiresAt: Date }

query(sql, { cache: LONG_CACHE })
query(sql, { cache: DAILY_CACHE, proxyCache: true })
query(sql, { cache: { expiresAt: new Date('2026-11-01T00:00:00Z') }, proxyCache: true })
```

TTL — целое неотрицательное число секунд. `until` означает ближайшую календарную границу
**UTC**: начало следующего часа, дня или месяца. Она вычисляется при фактическом запуске,
после ожидания очереди. Нулевая длительность или прошедший `expiresAt` не сохраняют новый
ответ в кеш и не добавляют proxy-заголовки. Срок локального кеша отсчитывается от запуска
запроса, не продлевается после загрузки и при переносе ответа в кеш компонента.

Константы: `SUPER_SHORT_CACHE` (5 с), `SHORT_CACHE` (10 с), `DEFAULT_CACHE` (60 с),
`MEDIUM_CACHE` (5 мин), `LONG_CACHE` (10 мин), `DAY_CACHE` (24 часа), `MONTH_CACHE` (30 дней),
`DAILY_CACHE` (до следующего дня UTC), `MONTHLY_CACHE` (до следующего месяца UTC),
`IMMUTABLE_CACHE` (до 2100-01-01 UTC). Старые `*_CACHE_SETTINGS` заменены этими
политиками; технические настройки ClickHouse остаются в `settings`.

`cache` поддерживает объект, `Ref` и getter. `useQueryStatParamsCache(params)` возвращает
реактивную политику: для конкретного игрока — `undefined`, для «за всё время» — MEDIUM,
для «последние X боёв» — SHORT, иначе DEFAULT. Передавай ref как `{ cache }`, чтобы
`queryComputed` учитывал смену политики. `queryAsync` по-прежнему выполняется один раз.

Политика преобразуется в `use_query_cache`, `query_cache_ttl` и `query_cache_tag`.
Явное `settings.use_query_cache = 0` сохраняется. Tag включает исходный пользовательский
тег и идентификатор политики; для календарной политики он меняется вместе с границей,
поэтому новый период не прочитает старую запись ClickHouse. Без `cache` настройки сервера
остаются прежними. См. [query cache ClickHouse](https://clickhouse.com/docs/operations/query-cache).

`allowCache` управляет только локальным кешем и объединением запросов в полёте, независимо
от ClickHouse и прокси. Без политики локальный кеш сохраняет прежнее поведение на время
жизни вкладки, если заголовки ответа не задают более короткий срок. Ключ локального кеша
учитывает SQL, формат, настройки и политику. `QueryResponse.cacheExpiresAt` содержит
абсолютную границу в миллисекундах (или `Infinity`); `createQueryCache<T>()` позволяет
компонентам сохранить этот срок: `cache.set(key, data, response.cacheExpiresAt)`.
`get`/`has` удаляют просроченные записи. Проверка происходит при обращении к кешу,
автоматической перезагрузки уже показанных данных по таймеру нет.

При чтении ответа учитываются `Cache-Control`, `Expires` и `Age`: срок от сервера может
сократить локальное хранение, но не продлить политику. Для cross-origin запросов сервер
должен открывать нужные заголовки через `Access-Control-Expose-Headers` (в частности `Age`).

### Заголовки внешнего кеша

`proxyCache: true` — отдельное разрешение, по умолчанию выключено и требует `cache`.
Сейчас оно включено для основной статистики техники, её истории, статистики коробок
(`/session/lootbox`, включая список контейнеров; для конкретного игрока TTL равен 0)
и сравнения версий (`/services/compare-versions`, TTL 24 часа для всех запросов страницы).
В таблице лидеров Натиска TTL равен часу, ключ включает время пересчёта из WebSocket
или загруженного снимка; без WebSocket-версии или при закрытом соединении актуальный
снимок запрашивается напрямую из БД без кеша. Графики без времени пересчёта также
выполняют полный запрос с пустой версией и TTL 0, без локального и прокси-кеша.
Встроенный query cache ClickHouse для лидерборда отключён: комментарии
меняют ключ прокси, но не AST-ключ ClickHouse (подробнее — [страницы](04-pages.md)).
Остальные запросы
переведены на политики без автоматического включения внешнего кеша.
Для таких запросов клиент также задаёт `wait_end_of_query=1` и
`send_progress_in_http_headers=0`: ClickHouse должен завершить расчёт до отправки
HTTP-статуса. Эти параметры входят в хеш, как и остальные настройки результата.
Для запросов с proxy-политикой fetch использует `credentials: 'omit'`: cookies сайта
не отправляются даже при same-origin `/api/db/`, иначе nginx возвращает BYPASS.
Явный заголовок `Authorization` от клиента ClickHouse сохраняется. Запросы без
proxy-политики сохраняют обычное поведение fetch.

- `X-Wotstat-Query-Cache-Key: <sha256>` — 64 шестнадцатеричных символа
- `X-Wotstat-Query-Cache-TTL: <seconds>` **либо**
  `X-Wotstat-Query-Cache-Until: <ISO UTC>`

`src/db/proxyCache.ts` получает окончательный HTTP-запрос через custom `fetch` клиента.
Хеш считается Web Crypto SHA-256 от UTF-8 представления следующего `JSON.stringify`:

```ts
[
  'wotstat-clickhouse',
  'public', // scope
  'POST',
  sortedParameters,
  ['ttl', ttlHeaderValue], // либо ['until', untilHeaderValue]
  body,
]
```

Этот fetch используется клиентом одного ClickHouse, поэтому идентификатор сервиса
всегда `wotstat-clickhouse`, без разбора домена и пути. Адрес прокси не участвует в хеше:
RU переиспользует основной кеш, прогретый прямыми запросами. Группа публичных данных
задаётся явно; ключ содержит только хеш, без префиксов.

`sortedParameters` — массив пар строк из `URLSearchParams`, отсортированный сначала по
ключу, потом по значению обычным сравнением строк (без localeCompare). Исключаются только
`query_id` и `query_cache_ttl`; остальные параметры, включая БД, форматирование и cache tag,
сохраняются. Тело хешируется точно в отправляемом виде, включая добавленный SDK `FORMAT`.
Пробелы SQL не нормализуются. Политика входит в ключ стабильным TTL или абсолютным сроком;
меняющийся остаток TTL ClickHouse на ключ не влияет. Отмена проверяется до и после
асинхронного хеширования. Требуется secure context с `crypto.subtle` (HTTPS или localhost).
В режиме `development` при `VITE_MODE_DEV_LOCAL === 'true'` модуль `src/db/devPolyfill/`
до создания клиента добавляет отсутствующие `crypto.randomUUID` и `crypto.subtle.digest`.
Полифил digest поддерживает только SHA-256 и лениво загружает локальную реализацию
из `src/db/devPolyfill/sha256.ts`, поэтому dev по HTTP-адресу локальной сети работает
без дополнительных зависимостей и с тем же значением ключа. В прод-сборке полифилы не включаются.

Для cross-origin доступа нужно разрешить три новых заголовка в CORS.
В `Access-Control-Allow-Headers` ответа OPTIONS нужно добавить `X-Wotstat-Query-Cache-Key`,
`X-Wotstat-Query-Cache-TTL`, `X-Wotstat-Query-Cache-Until`. Для чтения возраста ответа
добавить `Age, Date` к `Access-Control-Expose-Headers`, сохранив существующие заголовки
ClickHouse. Это разрешает запросы из браузера, но не включает кеширование на сервере.

### Кеш запросов на RU и основном nginx

Конфигурации находятся в соседнем репозитории `../server-config/etc/nginx-ru/`
и `../server-config/etc/nginx/`:
`conf.d/query-cache.conf`, `snippets/query-cache.conf`, `njs/query-cache.js`.
На RU кеш подключается к `/api/db/` в `ru.wotstat.info` и к отдельному серверу
`ru.db.wotstat.info`, который имеет приоритет над регулярным выражением общего
конфига поддоменов. Основной сервер кеширует в `db.wotstat.info`; маршрут
`wotstat.info/api/db/` сохраняет локальный переход туда и существующие лимиты запросов.
Требуются `ngx_http_js_module` с движком QuickJS и `ngx_http_gunzip_module`.
Обе конфигурации проверены на
nginx 1.30.5 / njs 1.0.1. Пользователь подтвердил установку на RU и основном сервере.

- Разрешение на кеширование: POST, ключ SHA-256, ровно один из TTL/Until,
  срок не более 100 × 365 дней и группа `public`. Лимит одинаковый в основном Nginx,
  RU Nginx и Cloudflare Worker; он допускает `IMMUTABLE_CACHE` до 2100 года.
  Nginx определяет группу через `map $remote_user`
  для точных имён `public` и `internal-public` без проверки пароля. Запросы с cookie,
  заголовками `X-ClickHouse-*`, повторяющимися URL-параметрами, альтернативной
  авторизацией или сессией ClickHouse обходят кеш. Для кеширования требуется
  `wait_end_of_query=1`.
- На HIT используется присланный ключ без повторного SHA-256. Кеш содержит только
  ранее проверенные ответы группы `public`; это не механизм авторизации.
- При MISS nginx обращается через Unix socket к внутреннему обработчику того же
  nginx. Он пересчитывает точно такой же JSON-массив, как фронтенд, и проверяет хеш.
  Несовпадение даёт HTTP 400 без запроса к источнику и без записи в кеш.
- На RU проверенный запрос проксируется на основной сервер, на основном — в локальный
  ClickHouse. Только успешный HTTP 200 без
  `X-ClickHouse-Exception-Code`, `Set-Cookie`, `no-store/no-cache/private` разрешён
  к сохранению. Внутренний ответ задаёт `X-Accel-Expires: @<epoch-seconds>` для
  внешнего cache location. Данные ответа передаёт nginx, JS их не собирает в памяти.
- `proxy_cache_lock` объединяет конкурентные промахи до 130 секунд. Просроченные
  ответы не выдаются; фоновое обновление для запросов отключено. На основном Nginx
  дисковый лимит зоны — 10 ГиБ, удаление невостребованных записей — `inactive=30d`;
  на RU — 30 ГиБ и `inactive=90d`. Общая память ключей и метаданных (`keys_zone`) —
  64 МиБ на основном сервере и 128 МиБ на RU.
- `X-Wotstat-Query-Cache-Status` и `X-Cache-Status` возвращают HIT, MISS или BYPASS.
  MISS означает получение разрешённого к хранению ответа от источника; BYPASS —
  проход без кеша или ответ, который нельзя сохранить. Возраст HIT передаётся в
  `Age`, исходный срок сохраняется в `Cache-Control` и `Expires`.
  Все нужные заголовки открыты CORS.
- В `location @query_origin` основной nginx всегда запрашивает у ClickHouse
  `Accept-Encoding: gzip`; RU всегда отправляет основному `gzip, br`, как в проверенном
  маршруте через Cloudflare. Заголовок браузера на эти переходы не влияет, map для
  отдельных браузерных списков больше не нужен. Внутренние location используют
  `gzip off` и `gunzip off`, сохраняя полученное представление для записи в кеш.
- Оба кеша хранят один gzip-ответ на ключ. Если источник не сжимает ответ, допускается
  несжатое представление; фронтенд включает HTTP-сжатие в клиенте ClickHouse.
  `prepareFill` удаляет только `Accept-Encoding` из внутреннего `Vary`, сохраняя
  остальные поля и `*`. `responseHeaders` возвращает `Vary: Accept-Encoding` наружу
  уже после поиска в кеше. `proxy_ignore_headers Vary` не используется.
- Публичные location на обоих nginx используют `gunzip on` и `gzip_proxied any`:
  клиенту с поддержкой gzip передают сжатые байты, остальным распаковывают ответ
  после чтения из кеша. `gzip_vary off` предотвращает повторное добавление заголовка
  встроенным фильтром: его выставляет `responseHeaders`. Запрос без gzip, даже первый,
  не создаёт отдельный несжатый файл кеша. Cloudflare сам выбирает сжатие для браузера.
- На RU `X-Wotstat-Query-Cache-Upstream-Status` показывает статус основного кеша,
  если запрос действительно дошёл до него. Например, локальный MISS и upstream HIT
  означают заполнение RU из основного кеша без обращения к ClickHouse. При локальном
  HIT upstream-статус удаляется: сохранённый статус старого заполнения уже не актуален.

Повышение лимита с 31 дня до 100 × 365 дней проверено локально: оба Nginx и Worker
дают MISS → HIT для `IMMUTABLE_CACHE` до 2100 года и TTL два года, сохраняя срок ответа.
На живом RU и основном Nginx до применения обновления сроки больше 31 дня дают BYPASS.
Для применения обновить `njs/query-cache.js` на обоих Nginx, выполнить `nginx -t`
и reload, затем опубликовать Worker. Формат ключа не меняется, очистка кеша не нужна.

Клиент и сервер включают в хеш постоянный идентификатор `wotstat-clickhouse`.
Передача `X-Wotstat-Query-Endpoint` осталась в прокси-конфигах, но для вычисления
и проверки хеша этот заголовок больше не используется.
В `proxy_cache_key` обоих nginx используются `wotstat-clickhouse`, группа кеша,
присланный хеш и постоянный суффикс `|gzip`, без дополнительного публичного URL.
Суффикс обозначает сохранённое gzip-представление.
Сохранение публичного URL в nginx-ключе
разделяло бы кеш даже при одинаковом хеше. Прямой запрос и запрос через RU с
одинаковыми SQL, параметрами, группой и политикой используют одну запись
на основном сервере. Формат/БД остаются в хеше; параметры и тело не нормализуются иначе.

При заполнении из другого кеша срок ограничивается его `Cache-Control`, `Age` и `Expires`:
перенос ответа между серверами не начинает TTL заново. Проверены прямые MISS/HIT,
RU MISS → основной HIT после очистки только RU, сохранение срока и проверка хеша.
Проверка использовала два nginx
и HTTP-заглушку ClickHouse в локальном контейнере; это не проверка живого основного сервера.
После установки на обоих живых серверах проверены запросы `SELECT 1`: без Cookie —
MISS → HIT, с Cookie — BYPASS (на RU оба уровня). В изолированном браузерном контексте
same-origin запросы с cookie сайта воспроизвели проблему; `credentials: 'omit'` устраняет
её с сохранением явной Basic-авторизации.

Для общего ключа сначала обновляются `njs/query-cache.js` и `proxy_cache_key` в
`snippets/query-cache.conf` на обоих серверах, затем публикуется фронтенд и перезагружаются
открытые вкладки. Расчёт хеша на клиенте и сервере должен совпадать. Общий ключ требует
нового прогрева, удалять старые файлы кеша вручную не нужно. Проверка на двух nginx:
прямой MISS → RU MISS / upstream HIT, затем HIT через оба db-поддомена, один запрос
к источнику и прежняя дата истечения. Общий ключ подтверждён на живых серверах:
для одного SQL прямой запрос дал MISS → HIT, затем RU с `Accept-Encoding: gzip, br`
дал MISS / upstream HIT. При `gzip, deflate, br, zstd` и `br, gzip` RU получал
MISS / upstream MISS с тем же хешем из-за `Vary: Accept-Encoding`.

Для перехода на единый gzip обновляются три файла на каждом сервере:
`conf.d/query-cache.conf`, `snippets/query-cache.conf`, `njs/query-cache.js`.
Сначала основной nginx, затем RU; после полного обновления каждого —
`nginx -t && systemctl reload nginx`. Основной должен начать отдавать gzip до
переключения RU на постоянный список кодеков. Старые файлы удалит cache manager;
ручная очистка и публикация фронтенда не нужны. Установка этой версии на живых
серверах ещё не подтверждена.

Проверка нового варианта на двух локальных nginx использовала HTTP-заглушку с
настоящими gzip-байтами и клиент без автоматической распаковки. На всех четырёх
маршрутах gzip, Brotli-only, identity, `gzip;q=0` и отсутствие заголовка используют
один результат от источника; неподдерживающие gzip клиенты получают распакованный
ответ. Проверены заполнение RU из основного HIT первым identity-запросом,
сохранение срока кеша, объединение конкурентных запросов с разными кодеками,
BYPASS/ошибки/CORS и сохранение остальных Vary-полей. В каждом кеше физически
сохраняется один gzip-файл для проверенного общего запроса.

### Кеш SQL в Cloudflare Workers

Код и инструкция подключения подготовлены в соседнем репозитории
`../server-config/cloudflare/query-cache/`: `worker.js`, `wrangler.toml`, `README.md`.
Публикация в Cloudflare выполняется отдельно. Единственный маршрут —
`wotstat.info/api/db/*`; звёздочка нужна для query-параметров. Остальные страницы
и поддомены Worker не вызывают. `workers.dev` и preview URLs отключены в конфигурации.

Worker использует существующие заголовки фронтенда и отдельный namespace Cache API.
На HIT доверяет ключу, на MISS передаёт POST в nginx и сохраняет только разрешённый
успешный ответ со статусом nginx HIT/MISS. Условия допуска совпадают с nginx;
Cookie и запросы без разрешения обходят кеш. Ошибки и неизвестный Vary не сохраняются.
Срок ограничен политикой и оставшимся временем ответа nginx, без продления TTL.
SQL и ответ передаются потоком. У nginx запрашивается gzip; ключ кеша не зависит
от сжатия браузера. Наружу сохраняется `Vary: Accept-Encoding`.

На этом маршруте `X-Wotstat-Query-Cache-Status`/`X-Cache-Status` описывают Worker,
а `X-Wotstat-Query-Cache-Upstream-Status` — nginx, только если к нему было обращение.
На Worker HIT upstream-статус отсутствует. Cache API локален для дата-центра,
без Tiered Cache; HIT всё равно является вызовом Worker. `CF-Cache-Status` не
используется как индикатор нашего кеша.
Проверена локальная цепочка workerd/Miniflare → nginx со сжатием, TTL/Until,
разными SQL и проверкой хеша. Подключение опубликованного маршрута требует
отдельной проверки в Cloudflare. См. [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/).

## StatParams и генерация WHERE (`src/shared/legacyStatQuery/useQueryStatParams.ts`)

`shared/legacyStatQuery/` — адаптер совместимости общих фильтров старой инфографики.
В нём пока остаются модель `StatParams`, преобразование URL-параметров, SQL и политика кеша.
Новые страницы задают собственные параметры через универсальный `useQueryStorage`.

`useQueryStatParams()` собирает объект из refs `useStatQueryStorage()` (см. [10-query-storage.md](10-query-storage.md)). Массивы копируются, чтобы потребители не меняли состояние хранилища при сортировке:

```ts
type StatParams = {
  player: string | null        // ?nickname=
  level: TankLevel[] | null    // ?level=8,10   (1..11)
  types: TankType[] | null     // ?type=HT,MT   (LT|MT|HT|AT|SPG)
  tanks: string[] | null       // ?tank=ussr:R45_IS-7,...
  battleModes: BattleModeSelectionKey[]      // ?mode=random-domination,onslaught; [] — все
  period: 'allTime' | {type:'lastX',count} | {type:'fromTo',from,to} | {type:'fromToNow',from}
          // ?lastX= | ?from=&to= | ?from=
  battleId: string[] | null    // ?battle-id= (приоритетнее периода)
}
```

`whereClause(params, {withWhere, isBattleStart, ignore, additional})` — собирает SQL `where ...`:
- фильтры по игроку/уровню/типу/танку/режиму;
- период через `id` (id = `timestamp_ms * 1e10`, см. `dateToDbIndex`) и `dateTime`;
- `lastX` — подзапрос последних N `Event_OnBattleStart.id`;
- `isBattleStart: true` — фильтр по `id`, иначе по `onBattleStartId` (события, привязанные к бою).

`whereClauseColumns(params)` — список колонок, участвующих в фильтре; нужен для выбора materialized view.

`shared/game/domain/battleModes/battleModeFilter.ts` — общий SQL-фильтр режимов для StatParams, карт и техники. Он разворачивает
читаемые ключи через `battleModeTargets`, удаляет покрытые цели, оставляет прямое условие
`battleMode in (...)` и при необходимости добавляет OR точных пар `battleMode/battleGameplay`.
Колонка `battleGameplay` требуется только при оставшихся ограничениях по геймплею;
это учитывается при выборе MV. При заданном `battleId` общий фильтр режимов игнорируется.

`PlayerResultTable` строит места по длине агрегированных массивов результатов, без словаря
размеров команд и без отсеивания боёв по числу игроков. `avgForEach` / `avgForEachMerge`
усредняют каждое место по боям, в которых оно присутствует, в том числе при нескольких режимах.

## Materialized Views (`src/db/schema.ts`)

Для тяжёлых агрегаций есть семейства MV с разными наборами колонок-ключей (`player_coverage_*`, `team_results_mv`, `accuracy_hit_points_*`, `Event_OnShot_*`). Выбор оптимального:

## Таблицы БД

Полный каталог таблиц базы `WOT` с колонками, типами и значениями категориальных полей (режимы, типы/роли танков, нации, снаряды, карты и т.п.) вынесен в отдельный справочник — [09-database-schema.md](09-database-schema.md).

`session/vehicles` использует общий построитель `vehicleStatisticsQuery.ts`. Основная таблица
выбирает источник по группировке и фильтрам:

| Запрос | Источник |
| --- | --- |
| Танки, фильтры только по региону/режиму/геймплею | `PlayerBattleDailyStatistics` |
| Уровни, классы, классы по уровням с теми же фильтрами | `PlayerBattleDailyStatisticsByClassLevel` |
| Категории с переданным `VehicleSelection` по нации или конкретному танку | `PlayerBattleDailyStatistics` |
| Есть карта, взводность, результат или уровень боя | `PlayerBattleResults` |
| Архивные части истории; текущая часть со сложными фильтрами/разбиением | `PlayerBattleResults` |

Последний день танка/категории определяется после фильтрации: `max(day)` непосредственно
из выбранной витрины, для raw — `max(lastDay)` из `PlayerBattleLatestDays`. `processedUntil`
не участвует в выборе периода. Фильтры уровней и классов поддерживаются обеими витринами;
локальные фильтры таблицы по-прежнему применяются на клиенте. Старые `VehiclesStatistics`
и `VehiclesStatisticsByBattleMode` сохранены в БД для сравнения.

`vehicleStatisticsQueries` строит два базовых SQL-запроса основной таблицы и предоставляет `column(group, rows)` для групп загрузки метрик. Метод возвращает `{ sql, cache }` или `null`, если отдельный запрос не нужен. Базовый ответ содержит только ключ, танк, уровень, тип, регион, последний день, актуальность, число боёв и игроков. Опорный `actualDay` — наиболее частый `latestDay` среди групп в диапазоне `max(latestDay) - 2 .. max(latestDay)` включительно; при равной частоте выбирается более поздняя дата. Актуальны группы с `latestDay >= actualDay`, остальные неактуальны. Обе части читают индивидуальные 1/7/30-дневные окна через набор `(ключ группы, day)`. Для актуальных дополнительно задан общий диапазон `actualDay - (days - 1) .. max(latestDay)`, для неактуальных — от их минимальной последней даты минус `days - 1` до максимальной. Явные границы позволяют отсекать партиции независимо. Каждая группа принадлежит одному запросу, поэтому на клиенте объединяются готовые строки без повторного усреднения или слияния квантилей. Поле ответа `isActual` управляет подписью даты в UI; фронт не вычисляет актуальность повторно по загруженным строкам. Выведенные танки и режимы сохраняют свой последний доступный период.

`vehicleListTable/useVehicleTableStatistics.ts` сначала последовательно получает базовые строки актуальной и, при необходимости, неактуальной части. Затем загружаются выбранные метрики актуальных, после них — неактуальных строк, с общей группой `concurrency` из `src/db`. Лимит передаётся в `createConcurrencyGroup(limit)`: таблица использует 1 (последовательная загрузка), график сравнения — 5. Бои и игроки уже есть в базовом ответе. Для списка танков неактуальная часть выключена галочкой «Только актуальные»; категории всегда загружаются полностью. До завершения всей последовательности таблица показывает общий спиннер, частичные данные не публикуются. Счётчик сразу показывает «0 из N»: базовые запросы и один набор уникальных пакетов выбранных метрик для первой незагруженной части. Метрики остальных частей добавляются после подтверждения наличия данных, без предварительного удвоения максимума. После базовых ответов исключаются метрики пустых частей и обнаруженные ответы из кеша. Уникальный завершённый SQL добавляет один шаг независимо от числа возвращённых колонок. Добавление агрегации уже выбранной метрики не меняет план и не сбрасывает счётчик.

Запрос показателя возвращает `rowKey` и именованные поля всех его агрегаций: среднее, минимум, максимум, девять квантилей и долю нулей. Все агрегации одного показателя ссылаются на один объект `MetricData` с постоянным набором и порядком SQL-выражений. Поэтому любая агрегация даёт одинаковый SQL и ключ кеша. Загрузчик следит за набором `data.column.key`, а не за набором выбранных вариантов: добавление уже загруженного квантиля не перезапускает загрузку. Квантили используют одно выражение `quantilesTDigest` для raw или `quantilesTDigestMerge` для витрин; все агрегации показателя читаются вместе. Для производных показателей среднее остаётся отношением сумм, остальные агрегации считаются по индивидуальному значению. Показатели без дополнительных агрегаций возвращают одно поле. Последние даты берутся из базовых строк и повторно не запрашиваются: для каждой группы сохранено её окно 1/7/30 дней. Явные нижняя и верхняя границы `day` отсекают лишние партиции. Для актуальных групп с общей последней датой запрос метрики передаёт только дату и диапазон дней, без списка ключей и `ARRAY JOIN`. `HAVING max(day) >= firstDay` исключает группы, устаревшие относительно этой даты. Если среди актуальных есть группы с более свежими датами, передаются только их ключи: `multiIf` задаёт им собственные границы периода. Неактуальная часть сохраняет полный набор `(rowKey, day)` и индивидуальные окна. Даты и ключи исключений сортируются перед включением в SQL, поэтому порядок строк и выбранных колонок не меняет ключ кеша. Результаты объединяются по `rowKey`, а не по позиции в ответе.

Успешные ответы кешируются раздельно по SQL. Базовый запрос таблицы использует `LONG_CACHE`
(10 минут): он определяет последние даты динамически и должен увидеть обновление витрины.
Метрики используют TTL 7 дней; их SQL содержит точные границы из базового ответа, без
дополнительного ограничения сегодняшней датой. Пока даты данных не изменились, тело и
ключ запроса метрик одинаковы и до, и после полуночи, в том числе на границе месяца.
Исторический backfill может изменить такой ответ до истечения TTL — для немедленного
отображения исправлений понадобится сброс кеша. Добавление нового показателя догружает только его набор; переключение или добавление агрегаций уже загруженного показателя и перестановка колонок не запускают запросов. Одинаковые SQL выбранных колонок объединяются в одну задачу. Нужные запросы в полёте переиспользуются при смене столбцов, запрос набора отменяется только после удаления всех его выбранных агрегаций, включая ожидающие задачи. Смена фильтров/периода/группировки отменяет устаревшие запросы, уход со страницы — все запросы таблицы. Повтор после ошибки использует уже успешные части и заново запрашивает недостающие. Если все части уже в кеше, спиннер не появляется. Формат ответа — `JSONCompact`.

`PlayerBattleLatestDays` — ежедневный срез по полному ключу фильтров; его заменяет `player_battle_latest_days_rmv` (`REFRESH EVERY 1 DAY OFFSET 10 MINUTE`, только завершённые UTC-дни). Срез предназначен для текущей таблицы, не для восстановления последних дат на произвольную дату в прошлом. Пользователю `public` нужно право `SELECT` на raw, срез последних дат и обе дневные витрины; выдаёт его владелец БД вручную.

`vehicleMetrics/vehicleMetrics.ts` содержит единый каталог метрик и плиток. Локальная фабрика `statisticMetric`
принимает `sql` (raw) и `dailySql` (витрины), создаёт фиксированные варианты и связывает их
с одним объектом `MetricData`. Фабрика `snapshotMetrics` создаёт те же общие определения
для планок API. Глобальных типов `battle`/`threshold` и ветвления по ним в загрузчиках нет.

`shared/metricData/utils/types.ts` задаёт общий интерфейс `MetricData`: необязательную группу
загрузки столбцов `column: MetricColumnData` и независимый `history(context)`. Группа содержит
стабильный `key` и `query(context)`; все её метрики используют один объект и полный набор
возвращаемых столбцов. Реализации возвращают готовые планы с политиками кеша.
Отсутствие `column` означает, что значение уже есть в базовых строках
таблицы (бои и игроки). `shared/metricData/battle/` содержит расчёты статистики, выбор raw/витрин
и запросы базовых строк; `snapshotMetricData/` — получение снимков API и взвешивание планок групп.
Общая часть загрузчика не знает SQL-выражений, таблиц БД или разновидности метрики.
Группа загрузки не связана с принадлежностью значений плитке: основные и нестандартные
процентили одного источника API используют общий пакет столбцов, сохраняя отдельные запросы
истории. Агрегации боевого показателя загружаются вместе и для таблицы, и для истории.
Бои/победы/выжившие складываются, игроки объединяются через `uniqIfMerge(playersState)`,
средние — `sum(metricSum) / sum(battles)`, производные средние — отношения исходных сумм.
Для nullable `stunDuration` и производных распределений знаменатель доли нулей и проверка
пустого распределения используют `ValueCount`; среднее `stunDuration` тоже делится на него.
Минимумы/максимумы объединяются через `minOrNull`/`maxOrNull`, квантили — через
`quantilesTDigestMerge` с исходными девятью уровнями. Готовые дневные средние/квантили
не усредняются. Набор полей и SQL пакета не зависят от выбранной агрегации.

Проверка переключения 4 октября 2026: на локальных данных все 589 выражений сопоставлены
с raw, включая NULL, архивные группы, более свежие группы относительно опорного дня и
периоды 1/7/30 дней. Через публичный прокси проверены реальные базовые запросы и пакеты
урона, оглушения и доли содействия. Для RU / REGULAR / 30 дней база актуальных танков
(964 строки) заняла 1,19 с, метрики — 0,16–0,28 с; база классов по уровням (47 строк) —
0,57 с, метрики — около 0,04 с. Это отдельные серверные замеры с `max_threads = 2` и
`use_query_cache = 0`, без времени сети и рендера, не гарантия задержки для всех фильтров.

Основная таблица запрашивает все агрегации только выбранных показателей, кроме обязательных боёв/игроков. История и сравнение загружаются отдельными пакетами, описанными ниже. Кеш вкладки и настройки серверного кеша используют явные UTC-даты в SQL; `query_cache_nondeterministic_function_handling = 'save'` разрешает кешировать `any` и TDigest ([документация ClickHouse](https://clickhouse.com/docs/operations/query-cache)).

### Планки из публичного API игры

Разделы `mastery` и `marks` единого каталога используют фабрику `snapshotMetrics`:
она связывает фиксированные процентили и плитки с загрузкой снимков API.
`shared/metricData/snapshotMetricData/snapshotMetricData.ts` получает имена источников через `tables` в каталоге:
`history` — `MasteryInfo` / `MoeInfo`, `latest` — `MasteryInfoLatest` / `MoeInfoLatest`.
Событийные `Event_OnMoeInfo`, `GameMoeInfoLatest` и `GameMoeInfo` не используются.
Исторические API-таблицы имеют ключ `(region, tag, updatedAt)` и не содержат боевых измерений.
Планка отдельного танка не зависит от фильтров боёв. Для уровней, типов и типов по уровням
показывается среднее планок, взвешенное по числу участий танков в боях WotStat.
Режим, карта, взвод, результат и уровень боя влияют на состав группы и веса танков.
Значения и история доступны при выборе одного региона; при нескольких регионах остаются пустыми.
В селекторе нет отдельного агрегатора для планок: тот же процент обозначает планку танка
или взвешенное среднее группы.

Таблица загружает все доступные в каталоге процентили выбранного источника одним запросом:
11 значений из `MasteryInfoLatest` и 9 из `MoeInfoLatest`. При выборе обоих источников нужны два запроса;
источник без выбранных столбцов не загружается. Состав и порядок полей фиксированы каталогом,
поэтому выбор другого процента в той же группе не меняет SQL, ключ кеша и план загрузки.
Для отдельных танков запрос читает обычные колонки `pN` из Latest с `FINAL`, без агрегации и ограничения `beforeDay`:
API публикует уже сформированные планки, поэтому готовые сегодняшние снимки тоже доступны.
Период боевой статистики 1/7/30 дней не влияет на результат.
Запрос получает все танки региона без списка `tag in (...)`; актуальная и выведенная техника
используют одинаковый SQL и общий кеш. Загрузчик сопоставляет ответ со строками таблицы по `rowKey`.

В группировках `weightedSnapshots.ts` сначала считает бои по танку и ключу группы за один
последний завершённый UTC-день (`beforeDay - 1`), затем соединяет веса с Latest по тегу.
В агрегат попадают только снимки за общий последний день API выбранного региона и источника;
архивные планки не смешиваются с актуальными. Формула — `sum(планка × бои) / sum(бои)`.
Период таблицы 1/7/30 дней не меняет ни веса, ни планки. Нет боёв за вчера или подходящих снимков —
значение пустое. Это относится и к режимам, в которых вчера не было боёв.
Танк без подходящей планки исключается вместе со своим весом; нулевая планка учитывается.
Тип и уровень берутся из выбранных результатов боёв, фильтры выбора техники также применяются
к весам. `vehicleGroupingSql` задаёт одинаковые ключи строк для боевой статистики и планок.
Для простых фильтров веса читаются из `PlayerBattleDailyStatistics`, для детальных — из
`PlayerBattleResults`. JOIN выполняется после агрегации боёв (`query-join-filter-before`).
Все процентили источника по-прежнему возвращаются одним запросом, общая загрузка столбцов не меняется.

Фильтр региона сохраняет использование префикса ключа (`schema-pk-filter-on-orderby`).
Общие `VEHICLE_STATISTICS_QUERY_OPTIONS` задают `JSONCompact` для таблицы, истории и сравнения:
ключи колонок передаются один раз в `meta`, а строки — массивами. Клиент восстанавливает объекты
для существующих загрузчиков. HTTP gzip сжимает повторяющиеся даты без отдельного словаря.
`masteryUpdatedDay`/`marksUpdatedDay` содержат её дату для tooltip ячейки; имя поля задано
через `updatedDayField` в описании метрики. Кеш такого запроса — 10 минут,
поскольку последняя планка может обновиться без изменения дат боевой статистики.
Боевые столбцы сохраняют прежний кеш 7 дней для фиксированных окон.

Latest-таблицы используют `ReplacingMergeTree(version) ORDER BY (region, tag)` без партиционирования.
`version UInt64` — материализованная упаковка двух UInt32 Unix timestamps: `updatedAt` в старших
32 битах, `dateTime` в младших. Поэтому исторический backfill не заменяет более свежий снимок,
а при одинаковой дате API побеждает более поздняя загрузка. Инкрементальные MV переносят вставленные
снимки из исходных таблиц, первоначальное заполнение выбирает целые последние строки через `argMax`.
Фоновое слияние не заменяет `FINAL` при чтении (`insert-mutation-avoid-update`).

[Миграция Latest](sql/vehicle-api-latest.sql) выполнена владельцем БД и проверена 23 октября 2026.
Старая `MoeInfoLatest` сохранена под именем `GameMoeInfoLatest`, её событийная MV пересоздана
как `game_moe_info_latest_mv`. При переносе приём `Event_OnMoeInfo` приостанавливается:
переименование цели само по себе не меняет `TO` существующей MV. Новые API-таблицы и их заполнение
создаются отдельно. Все процентили и даты 3921 снимка мастеров и 3919 снимков отметок совпали
с последними строками исходных таблиц во всех четырёх представленных регионах.
Оба запроса каталога проверены через публичный HTTP API с клиентом фронтенда и `JSONCompact`.

История отдельного танка запрашивает только выбранный процентиль. Дата действия планки на графике —
UTC-дата `updatedAt + 2 дня`: API датирует снимок двумя днями раньше его актуальности в игре.
Сдвиг применяется до группировки по дням, неделям и месяцам; границы запросов переводятся обратно
в исходную дату через `updatedAt >= from - 2 дня` / `< until - 2 дня`. Фильтры региона и танка
сохраняют использование префикса ключа (`schema-pk-filter-on-orderby`). `dateTime` означает время
загрузки и разрешает повторные снимки. Дневная история включает готовую планку за сегодняшний день;
общая ось графика охватывает целиком последний загруженный период. За неделю/месяц выбирается
последнее значение завершённого периода по дате действия. История боевой статистики не сдвигается.

История группы сначала выбирает один снимок на танк и день действия через
`argMax(pN, tuple(updatedAt, dateTime))`. Повторная загрузка снимка не увеличивает его вес.
Отдельно считаются бои каждого танка за тот же день, с фильтрами страницы и выборки техники.
После JOIN по тегу и дню рассчитывается взвешенное среднее. Дни без API-снимка не заполняются
старой планкой. Сегодняшняя точка группы не выводится: её веса ещё неполные.
За неделю/месяц берётся последний дневной результат завершённого периода, а не среднее по дням.
Один запрос истории группы возвращает все процентили источника, поэтому переключение процента
переиспользует тот же SQL и кеш. История и сравнение используют общий загрузчик без особых веток.

Текущий отрезок групповой истории с простыми фильтрами читает веса из дневной витрины танков;
архив и детальные фильтры — из `PlayerBattleResults`. Условие `day in (дни снимков API)`
отсекает партиции, для которых планок нет, включая пустые архивные диапазоны.
Отдельная MV не требуется для корректности. Если нагрузка архивных запросов станет существенной,
кандидат на оптимизацию — узкая витрина дневных счётчиков боёв за всю историю; планки можно
по-прежнему присоединять при чтении, сохраняя возможность их исправления и backfill.

ожидается исторический backfill.

### Загрузка истории техники

`timeSeries/vehicleHistoryQuery.ts` обращается к `data.history` выбранной метрики.
`vehicleHistoryRanges(beforeDay, step)` из `shared/metricData/utils/historyRanges.ts` разбивает историю на непересекающиеся интервалы:

1. Вся история до начала текущего года.
2. С начала года до начала текущего месяца.
3. Остаток до последнего завершённого периода выбранного шага.

Все границы исключающие сверху. Для 2026-10-04 при шаге «день»: до 2026-01-01,
[2026-01-01, 2026-10-01), [2026-10-01, 2026-10-04). Каждая часть остаётся в выбранном
шаге графика: годовой запрос при дневном шаге возвращает дни, а не годовую сумму.
Для недель все границы округляются вниз до понедельника; например, граница 2026 года —
2025-12-29. Переходная неделя целиком относится к следующей части. Последняя незавершённая
неделя/месяц не загружается. Пустые интервалы не создаются; для месяцев третьего запроса нет.
Так каждая точка считается целиком в БД, уникальные игроки и квантили не объединяются
из готовых дневных чисел в браузере. Это решение под наш график (`derived`);
явные границы дат сохраняют отсечение месячных партиций (`schema-pk-filter-on-orderby`).

Первые две части всегда читают `PlayerBattleResults`. Только третий, текущий отрезок
использует дневную витрину, если нет фильтров карты/взвода/результата/уровня боя и разбиения
графика. `vehicleDailyStatisticsTable` задаёт общие с таблицей правила: конкретный танк
или нация требуют `PlayerBattleDailyStatistics`, категории без них используют
`PlayerBattleDailyStatisticsByClassLevel`. И база (бои/игроки), и метрика читают один источник;
`dailySql` объединяет состояния, включая уникальных игроков и квантили за целую неделю.
Месячный шаг не имеет третьей части и остаётся на raw.

Для этого согласовано расширение обеих витрин до 42 календарных дней относительно
последнего дня каждого ключа: запас покрывает начало недели в предыдущем месяце.
SQL для ручного применения — [расширение до 42 дней](../.local/sql/player-battle-daily-statistics-42-days.sql).
Он меняет запросы MV, обновляет `PlayerBattleLatestDays` по восстановленному raw,
досчитывает отсутствующие ключи/дни (в том числе архивные и впервые появившиеся в октябре)
и запускает refresh. Сначала нужно подключить постоянное наполнение raw и закрыть разрыв
после сентября. Применение ещё не подтверждено; перед ним витрины содержат 30-дневные окна.
Периоды основной таблицы остаются 1/7/30 дней. `processedUntil` на фронте не проверяется:
до завершения refresh график показывает доступный срез без дополнительного запроса к raw.
Небольшое отставание принято пользователем (`derived`, правило `query-mv-refreshable`).

Общий `timeSeries/useVehicleHistories.ts` используется раскрытыми графиками и сравнением.
Для каждого источника сначала параллельно загружаются части с `battles` и `playerCount`,
затем — части группы загрузки выбранной метрики с полным набором вариантов (среднее, min/max,
доля нулей и все девять квантилей), также параллельно. Пустая базовая часть не требует запроса метрики.
Выбор боёв/игроков вообще не создаёт запросов метрики. Ответы объединяются по
`(periodStart, splitKey)`, базовые данные кеша не изменяются. Пороги и сглаживание остаются
локальными и не влияют на SQL. При переключении между агрегациями одной метрики SQL
совпадает, загрузка не перезапускается; другая метрика переиспользует базу, включая запросы в полёте.

Формат ответов — `JSONCompact`. Общая группа concurrency ограничивает загрузчик пятью
запросами. Каждый план источника получает `createOrderedGroup()`: оставшиеся запросы
ранних танков имеют приоритет перед ожидающими запросами следующих. Поэтому история
каждого танка становится доступна по мере завершения, без обхода всех танков отдельно
для каждой части. Лимит относится к запросам, а не к числу танков; одновременно могут
грузиться несколько частей одного танка и часть следующего. Несколько источников одного
загрузчика разделяют одинаковые запросы. Удаление источника, смена фильтров/шага/разбиения
отменяют только запросы без оставшихся потребителей; закрытие графика отменяет все его
запросы. Успешные части остаются в кеше вкладки и доступны также другому графику.
Повтор после ошибки догружает недостающее, без случайных комментариев или счётчика retry в SQL.

SQL архивных частей не содержит сегодняшней даты или `now()` и меняется только при
смене соответствующей календарной границы. Первые две части используют `IMMUTABLE_CACHE`
до 2100-01-01 UTC, остаток — `DAILY_CACHE`.
Общий query-хелпер формирует TTL и tag политики для ClickHouse, а также заголовки
будущего внешнего кеша. Локальные кеши таблицы и истории сохраняют срок из ответа.
Сами внешние кеши здесь не настраиваются.
После исправления старых raw-данных их закешированные ответы потребуется инвалидировать.

Проверка: 42 локальных SELECT-сравнения с цельной агрегацией по raw на границах
месяцев/лет/недель, включая разбиение по результату. В браузере проверены JSONCompact,
порядок «база → метрика», переключение среднего на медиану без запроса, смена метрики без
повторной базы и переиспользование загруженной истории в сравнении.
После подключения витрин ещё 54 локальных SELECT-сравнения подтвердили совпадение
текущего отрезка с raw для танка, категории и нации: бои/игроки, распределения урона,
nullable-оглушения и производного отношения. Проверена неделя с 2026-02-23 при cutoff
2026-03-31. Отдельно проверены дозаполнение до 42 дней, повтор/продолжение без дубликатов
и следующий refresh обеих витрин по всем 230 полям агрегатов.

[SQL создания и заполнения PlayerBattleResults](../.local/sql/player-battle-results.md) хранится в `.local/sql`; каталог `.local` не хранится в Git. SQL выполняет пользователь вручную. Историческое заполнение проверено до сентября 2026 включительно; дневные витрины метрик созданы и обновлены, автоматическое поступление новых результатов пока не подтверждено.

Подготовлен порядок восстановления после сентября:
[incremental MV](../.local/sql/01-player-battle-results-live.sql) из существующего
`DeduplicatedBattleResults` → [backfill разрыва](../.local/sql/02-player-battle-results-gap.sql)
из `Event_OnBattleResult` → расширение обеих дневных витрин до 42 дней.
Обычная MV без временных условий начинает работать после CREATE, расписание ей не нужно
(`query-mv-incremental`). После появления октябрьских строк время первого связанного события
ищется в `Event_OnBattleResult` по `arenaId`. Backfill фиксирует свой `backfill_until`
после запуска MV и исключает уже записанные арены: минимум времени связанного события
сам по себе не гарантирует отсутствие разрыва на стыке асинхронных вставок. До последнего шага
дневные MV остановлены. Их продвинутый `processedUntil` не подтверждает полноту raw:
обновлённый backfill заполняет отсутствующие дни независимо от этого курсора.

Пользователь подтвердил создание [двух дневных витрин](../.local/sql/player-battle-daily-statistics.sql):
`PlayerBattleDailyStatistics` по региону/режиму/геймплею/танку/уровню/классу/дню и
`PlayerBattleDailyStatisticsByClassLevel` с теми же измерениями без танка. Каждая хранит до 30
календарных дней относительно последнего дня своего ключа; TTL нет, архивные окна сохраняются.
230 полей агрегатов (включая 45 общих состояний TDigest и одно состояние уникальных игроков)
покрывают все 589 вариантов метрик. При выборе нескольких регионов/режимов период на чтении
по-прежнему определяется после фильтрации для итогового танка или категории.

Обе таблицы — отдельные `MergeTree`, обе MV — refreshable с заменой результата.
Первая MV в 00:30 UTC читает прежнюю витрину, заменяет пересчитываемые дни свежими агрегатами
из raw и обрезает окна по ключам. `processedUntil` — единая исключительная верхняя граница
обработанного raw, а не последний бой: обычно читается вчера, повторный запуск заменяет вчера,
после пропуска читается весь недостающий диапазон. Необработанная пустая витрина остаётся пустой.
Вторая MV зависит от первой и целиком объединяет её дневные состояния в классы/уровни, raw не читает.
SQL создания останавливает оба расписания до отдельного исторического заполнения. Подготовлены
[первоначальное заполнение](../.local/sql/player-battle-daily-statistics-backfill.sql) и
[запуск MV с проверками](../.local/sql/player-battle-daily-statistics-start.sql). Пользователь подтвердил
первоначальный INSERT; первый refresh завершился `MEMORY_LIMIT_EXCEEDED` при сортировке
с лимитом 32 GB, отдельный SELECT потребовал 53,09 GiB. Backfill обновляет `PlayerBattleLatestDays`, сворачивает её до ключей витрины
и отдельно читает актуальные/архивные окна raw с явными границами дат. Один INSERT заполняет
первую таблицу; после его успешного завершения первый refresh второй MV заполняет категории.
Прерванный INSERT может записать часть строк: повторять его или включать MV без проверки нельзя.
Подготовлено [исправление запросов обеих MV](../.local/sql/player-battle-daily-statistics-fix-refresh-memory.sql):
последние дни вычисляются отдельно по ключам без состояний агрегатов, нужные строки выбираются
через набор `(ключ, день) IN (...)`. Оконная функция над широкими строками убрана; категории
отсекают старые дни до объединения состояний. Для вычисления последних дней первая MV дополнительно
читает только ключи и даты пересчитываемого диапазона raw. Файл меняет запросы через `MODIFY QUERY`
и повторяет refresh без нового backfill. После применения первый refresh снова достиг лимита
32 GB, теперь при чтении `damageAssistedRadioQuantilesState`. Подготовлена вторая редакция SQL:
4 потока чтения, один поток записи, блок чтения до 8192 строк, пороги объединения перед записью
8192 строки / 16 MiB вместо крупных стандартных блоков. 4 октября 2026 пользователь подтвердил
успешный refresh обеих MV с этими настройками и лимитом 32 GB. Ожидание `WAIT VIEW` составило
121,290 с для танков и 54,364 с для категорий. Точный пик RAM не предоставлен; отдельный вклад
размера блоков и параллелизма в устранение OOM не измерен.

Витрина танков содержит 490 082 строки и занимает 3,24 GiB, классов/уровней — 35 055 строк
и 1,04 GiB. Обе имеют статус `Scheduled`, пустую `exception` и следующий запуск 5 октября
в 00:30 UTC. `processedUntil` единый — 2026-10-04, но последний день фактов — 2026-09-30;
архивные дни 2024 года сохранены. Эти замеры ещё не проверяют добавление полноценного нового
дня raw. Опоздания в дни до пересчитываемого диапазона требуют отдельного пересчёта.
Фронт использует эти витрины для общих запросов основной таблицы по правилам выше.

Отдельный замер [SELECT обеих MV с FORMAT Null](../.local/sql/player-battle-daily-statistics-select-null.sql)
4 октября 2026: танки — 8,002 с / 632,41 MiB RAM, классы/уровни — 21,095 с / 16,13 GiB RAM.
В каждом запросе прочитано около 3,59 GB; обработано соответственно 1 470 246 и 980 164 строки.
Это вычисление без записи результата, а не полный refresh; пик CPU не измерен. Более ранние
121,290 с / 54,364 с `WAIT VIEW` относятся к другим запускам, поэтому разницу нельзя целиком
приписать записи без учёта кешей и условий выполнения.

Замеры refresh: [отчёт из query_log](../.local/sql/player-battle-refresh-usage.sql) выбирает
фоновые `Insert` с `log_comment = 'refresh of WOT.…'`, а не управляющие `SYSTEM WAIT VIEW`.
Он показывает время, отслеженный пик RAM, суммарное CPU-время и среднее число занятых
логических CPU. `peak_threads_usage` не является пиком загрузки CPU.
[Консольный монитор](../.local/sql/watch-player-battle-refresh.py) запускается на сервере
до refresh и раз в секунду читает `system.processes`; максимум CPU считается по разности
счётчиков между отсчётами. Это максимум по наблюдаемым интервалам, не мгновенный пик;
фоновые слияния и другие запросы в него не входят. Скрипт не запускает refresh и не пишет в БД.

Коротко: данные приходят от игрового мода в таблицы `Event_*` (сортировка по игроку, партиции по месяцу) и от микросервиса-cron в справочники (техника/карты/предметы по версиям + опрос игрового API: лидерборды Натиска, MoE, онлайн и пр.). Прочие базы (`MT-36-1`, `BOB25`, `Positions`, `WOTINSPECTOR`) — изолированные легаси, фронтом не используются.

Утилиты дат: `dateToDbIndex(date)` (ms→id-строка ×1e10), `dbIndexToDate`, `dateToDbDate` (YYYY-MM-DD), `semverCompareStartFrom('1.2.3')` — фильтр по `modVersionComparable`.

## Правила

- Значения в SQL интерполируются строками — не вставляй непроверенный пользовательский ввод без экранирования (существующий код экранирует минимально; ники приходят из URL).
- Не выводи колонки из `RESTRICTED_COLUMNS` (`systemInfo.*`).
- Для новых запросов выбирай политику `cache` по образцу соседних (частообновляемое → короткий TTL).
