# Ошибки написания кода

Краткий список общих антипаттернов написания кода, отмеченных пользователем. Прочитай его перед написанием или изменением кода и соблюдай правила в затрагиваемых участках.

## Как пополнять список

- Добавляй только подтверждённые пользователем правила написания кода, применимые в разных независимых задачах. Само по себе замечание или исправление не повод менять этот файл. Не выводи общие правила из частных замечаний самостоятельно.
- Проверка на общность: правило должно быть понятно и полезно без знания конкретной задачи, страницы или бага. Названия модулей допустимы в коротком примере, но не должны определять смысл правила.
- Не записывай требования к поведению отдельных функций и экранов, детали API, форматов, сборки, значения констант, отступы и историю исправлений. При необходимости такие сведения относятся к профильной документации. Не переноси туда каждую микроправку автоматически.
- Сначала проверь существующие пункты: уточни подходящий вместо добавления нового. Не дописывай в общее правило перечень частных случаев и исключений из очередной задачи.
- Пиши кратко: антипаттерн, предпочтительный подход и только при необходимости короткий пример. Не придумывай новые запреты от себя. Если общего правила нет, файл не меняй.

## 1. Сплошная стена кода без смысловых блоков

В длинных функциях отделяй пустой строкой самостоятельные этапы алгоритма. Связанные действия оставляй вместе. Короткие функции не дроби (см. правило 4).

Плохо — этапы слиты:

```ts
if (items.length === 0) return []
const cached = cache.get(key)
if (cached !== undefined) return cached
const active = items.filter(item => item.active)
const sorted = active.sort((a, b) => b.score - a.score)
const result = sorted.slice(0, limit)
cache.set(key, result)
return result
```

Хорошо — проверка входа, поиск в кеше, расчёт и сохранение читаются отдельно:

```ts
if (items.length === 0) return []

const cached = cache.get(key)
if (cached !== undefined) return cached

const active = items.filter(item => item.active)
const sorted = active.sort((a, b) => b.score - a.score)
const result = sorted.slice(0, limit)

cache.set(key, result)
return result
```

## 2. Громоздкие тернарные операторы

Если условие и результаты длинные, используй `if` с ранним `return`. Переносы строк не устраняют сложность выражения. Короткие понятные тернарные операторы допустимы.

Плохо:

```ts
return response.ok && response.data !== undefined ? { status: 'ready', value: normalize(response.data) } : { status: 'error', message: response.error }
```

Хорошо:

```ts
if (response.ok && response.data !== undefined)
  return { status: 'ready', value: normalize(response.data) }
return { status: 'error', message: response.error }
```

## 3. Лишние ветвления и вложенность вместо раннего возврата

Завершай ветку через `return`, когда дальнейший код ей не нужен. Не добавляй `else` после безусловного возврата.

Плохо — основной сценарий спрятан внутри нескольких проверок:

```ts
if (user) {
  if (user.active) {
    if (canEdit(user)) {
      return saveChanges(user)
    } else {
      return error('Нет прав на редактирование')
    }
  } else {
    return error('Аккаунт отключён')
  }
} else {
  return error('Пользователь не найден')
}
```

Хорошо — проверки завершаются сразу, основной сценарий остаётся на верхнем уровне:

```ts
if (!user) return error('Пользователь не найден')
if (!user.active) return error('Аккаунт отключён')
if (!canEdit(user)) return error('Нет прав на редактирование')
return saveChanges(user)
```

## 4. Лишнее дробление коротких функций

Разбивай код на смысловые блоки только там, где кода много и разделение помогает читать алгоритм. В примитивной функции из нескольких строк пустая строка между проверкой и возвратом не нужна. То же относится к коротким callback-функциям и простым веткам внутри больших функций.

Плохо:

```ts
finish() {
  if (this.bytes.length > MAX_BYTES) return invalid()

  return Uint8Array.from(this.bytes)
}
```

Хорошо:

```ts
finish() {
  if (this.bytes.length > MAX_BYTES) return invalid()
  return Uint8Array.from(this.bytes)
}
```

## 5. Сокращённые методы вместо стрелочных функций в объектах

В литералах объектов записывай функции как свойства со стрелочными функциями: `compact: (...) => { ... }`, а не сокращённые методы `compact(...) { ... }`.

Исключение — функции, которым нужны собственные `this` или `arguments`: для них оставляй обычный метод. Стрелочная функция берёт `this` и `arguments` из внешней области, поэтому такая замена изменила бы поведение.

Плохо:

```ts
const compactor = {
  compact(tag: string, contextRegion?: string): CompactValue {
    return tag
  },
}
```

Хорошо:

```ts
const compactor = {
  compact: (tag: string, contextRegion?: string): CompactValue => {
    return tag
  },
}
```

## 6. Служебные утилиты рядом с основными файлами

Основные файлы — самостоятельные модули или компоненты, определяющие назначение директории. Служебные файлы помогают им работать.

- Если служебные файлы нужны только одному модулю, собери их вместе с основным файлом в папку этого модуля. Дополнительная подпапка `utils/` внутри неё не нужна.
- Если в директории два и более основных модуля, общие для них служебные файлы размещай в `utils/`. Уже существующую общую утилиту переноси туда при добавлении второго модуля.

При переносе обновляй импорты и ссылки в документации.

Пример — таблицы кодов принадлежат одному модулю, упаковка идентификаторов используется несколькими:

```text
encoding/
  battleModes/
    battleModes.ts
    battleModeCodes.ts
  vehicles.ts
  arenas.ts
  utils/
    regionalIdPacking.ts
```

## 7. BEM-имена классов вместо иерархии селекторов

Для внутренних элементов компонента вместо `component__action` предпочитай короткие имена классов и вложенные селекторы: `.component { .action { ... } }`. Связь с компонентом выражается иерархией, а не повторением его имени в каждом классе.

Если иерархия неприменима, используй имя через дефис: `component-action`, без двойного подчёркивания.
