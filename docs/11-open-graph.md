# Open Graph

Карточки и метаданные живут в обычном `src/` рядом со страницами сайта. Студия —
асинхронная страница основного SPA по `/meta`. Второе приложение, `App`, содержит
только renderer карточек для Bun backend. Общего отдельного проекта `meta/` нет.
`src/meta/` содержит общие протоколы и механизм Open Graph. Дизайн карточек,
default-определение и общие контексты сайта находятся в `src/shared/ui/meta/`.

Основной сайт остаётся SPA. Сервис `analytics-frontend-meta` добавляет мета-теги
в собранный `index.html`, а PNG/JPEG получает отдельным запросом через Chromium.
Запрос HTML не запускает браузер. При первом прогреве он может ждать контексты
выбранного определения в пределах их `initialWaitMs`; затем метаданные вычисляются
синхронно из последнего успешного снимка.

Страница `/debug/meta` содержит только заголовок и ссылку на студию `/meta`.
Отдельных debug-страниц превью и категории Open Graph нет; тестовые карточки
и их определения сохранены для проверки в студии и renderer.

Debug-карточка `/debug/meta/time` (`/meta/cards/debug-time` в студии) показывает
дату и время UTC до секунд, зафиксированные при каждом монтировании карточки.
Кеш HTML выключен, картинка кешируется на секунду, а `revisionKey` меняется каждую секунду.
Запрос картинки, не обслуженный кешем, рендерит новое время.
Это позволяет проверять кеширование и обновление превью внешними сервисами.

Debug-карточка для URL `/debug/meta/vehicle?tag=ussr:R45_IS-7` расположена рядом с карточкой
задержки: `pages/debug/pages/meta/cards/vehicle/`. Карточка читает русское название
по составному ключу `(RU, RU, tag)` из `VehiclesLocalizationDictionary` через
`dictGetOrDefault` и завершает `useMetaReady` после ответа. Неизвестный тег показывает
«Танк не найден», отсутствующий/некорректный — подсказку без запроса. Ошибка БД
отклоняет готовность и не превращается в успешно отрендеренную картинку. SQL кешируется до конца UTC-дня;
кеш HTML и картинки debug-примера выключен.

Заголовок этого же примера берёт имя из общего контекста
`shared/ui/meta/contexts/vehicleNames.ts`: «ИС-7 — WotStat Analytics». Контекст загружает
словарь `(region = 'RU', locale = 'RU')` целиком при старте и раз в час. Первоначальное
ожидание ограничено тремя секундами. Если имени ещё нет, title —
«Название танка — WotStat Analytics». Vue-карточка продолжает выполнять
свой отдельный запрос через `useMetaReady`.

В сборке renderer `VITE_META_RENDERER=true` выбирает `/api/db/` локального origin.
Этот маршрут существует только на loopback-сервере Chromium в Bun. Он добавляет
серверную авторизацию и обращается к локальному Nginx; пароль не входит в артефакт.
Студия в основном SPA использует обычный публичный endpoint и те же запросы/ключи кеша.
Production-настройки и SQL-миграция описаны в соседних `analytics-frontend-meta/README.md`
и `server-config/README.md`.

## Разработка и сборка

```bash
bun run dev     # основной SPA, студия на http://localhost:5173/meta
bun run test    # тесты совместимости ссылок compare
bun run check   # тесты и обе проверки типов
bun run build   # тесты, проверка типов, SPA в dist/ и meta-артефакт в dist-meta/
bun run preview # собранный основной SPA со студией на /meta
```

Команды, зависимости, lockfile и TypeScript-конфигурации общие с frontend.
Карточки разрабатываются через студию основного SPA. Отдельный dev-сервер или preview
renderer не нужен: собранное приложение запускает Bun backend.
`tsconfig.json` проверяет весь `src/`; `tsconfig.node.json` — `vite.config.ts` и `vitePlugins/`
с типами Bun. `check` запускает тесты и обе проверки типов; `build` вызывает его
один раз перед сборкой всех целей.

```text
vite.config.ts          # общий конфиг SPA, renderer и серверного модуля
vitePlugins/metaDefinitions/ # AST-поиск определений и виртуальный каталог Vite
package.json            # проверки и общая команда сборки
build-meta.sh           # сборка renderer, server.mjs и копирование spa.html
src/
├─ pages/
│  ├─ metaStudio/        # /meta и /meta/cards/:id основного SPA
│  ├─ debug/pages/meta/
│  │  ├─ Index.vue     # /debug/meta: переход в студию
│  │  └─ cards/        # debug-карточки delayed и vehicle с meta-definition.ts
│  └─ infographics/pages/vehicles/meta/
│     ├─ definition/      # vehicles-meta-definition.ts и примеры для студии
│     ├─ table/           # карточка таблицы, компоненты строк и загрузчик
│     ├─ compare/         # карточка сравнения и загрузчик источников
│     │  └─ chart/        # статичный график на UniversalChart
│     ├─ VehiclesMetaFrame.vue
│     └─ utils/           # общие URL-параметры, форматирование, подписи и готовность
├─ shared/ui/meta/
│  ├─ components/
│  │  ├─ MetaCard.vue    # слоты карточки, готовое содержимое и разделители
│  │  ├─ MetaCardBackground.vue # базовый слой и палитра подписей
│  │  ├─ MetaCardPattern.vue # точки, крестики, шум или SVG
│  │  ├─ backgrounds/    # отдельные Vue-компоненты фонов
│  │  ├─ assets/         # статические SVG-текстуры
│  │  └─ utils/
│  │     ├─ backgrounds.ts # каталог компонентов для студии
│  │     ├─ palette.ts   # цвета и локальный контекст палитры
│  │     └─ pattern.ts   # общие props паттерна
│  ├─ contexts/
│  │  └─ vehicleNames.ts # общий контекст названий техники
│  └─ generalMetaCard/
│     ├─ meta-definition.ts
│     └─ GeneralMetaCard.vue # общая карточка с двухцветным брендом без шапки
└─ meta/
   ├─ renderer/
   │  ├─ index.html      # HTML-точка входа renderer
   │  ├─ main.ts         # монтирование App
   │  └─ App.vue         # полотно, context, prepare, ожидание готовности и reset
   ├─ utils.ts           # типы, форматы и чистые хелперы
   ├─ definitions.ts     # автокаталог и выбор определения по URL
   ├─ resolver.ts        # resolver с контекстами; точка входа server.mjs
   ├─ pageMeta.ts        # метаданные SPA по URL и реактивные overrides страниц
   ├─ context/           # типы контекстов, загрузка, запросы и адаптация для студии
   └─ cards/
      ├─ CardSurface.vue # выбор компонента и размер полотна
      └─ useMetaReady.ts # асинхронная готовность карточки
```

Команда `build` в `package.json` последовательно запускает `check`, сборку SPA в `dist/`
и `sh build-meta.sh` через `&&`: следующий этап выполняется только после успешного
завершения предыдущего. Скрипт собирает renderer в `dist-meta/client/`, серверный
модуль в `dist-meta/server.mjs` и копирует `dist/index.html` в `dist-meta/spa.html`.
`set -eu` останавливает скрипт при ошибке. Для отдельного запуска `sh build-meta.sh`
уже должен быть собран основной SPA.
Все цели используют корневой `vite.config.ts` с тремя конфигурациями верхнего уровня:
`mainConfig`, `metaRendererConfig` и `metaServerConfig`. Внутри конфигураций нет
условий выбора цели; в `defineConfig` остаётся только выбор нужного конфига.
Конфиг выбирается только по `BUILD_TARGET`: `main`, `meta-renderer` или `meta-server`.
Без переменной используется `main`; неизвестное значение останавливает запуск с ошибкой.
`dev` и `preview` используют `main` по умолчанию, а команда `build` последовательно
собирает `main`, `meta-renderer` и `meta-server`.
Серверная точка входа `build.ssr` задана непосредственно в `metaServerConfig`.
Режим `mode` остаётся `development` для разработки и `prod` для сборки.
Примеры карточек — статические массивы имён и готовых URL в `examples.ts`
рядом с определением. Они импортируются обычным статическим импортом и не зависят
от кодека ссылок или браузерных каталогов. Генерация при запуске, top-level `await`
и отдельные флаги или плагины для примеров не нужны.
Плагины Markdown, Vue DevTools и visualizer
подключаются только для основного SPA.
Неудачная сборка останавливает команду, её результат не публикуется.
Артефакт передаётся на сервер только после успешного завершения всей команды сборки.
Сборка `server.mjs` использует Vite SSR как режим упаковки модуля, без SSR страниц.
Точка входа — непосредственно `meta/resolver.ts`, который также экспортирует `formats`.
Плагин `meta-definitions` во всех трёх целях генерирует виртуальный модуль
`virtual:meta-definitions` со статическими импортами найденных экспортов.
Полученный серверный модуль не зависит от Vue и DOM;
Bun загружает его при старте, создаёт клиент через `createDatabase(database)`
и передаёт его `query` в `createMetaResolver(query)`.
Контексты и их загрузчики включены в этот же `server.mjs`; отдельной сборки контекстов нет.

```text
dist/                   # основной SPA, включая асинхронную студию
dist-meta/
├─ server.mjs           # resolver, контексты, клиент запросов и форматы изображений
├─ spa.html             # копия dist/index.html той же сборки
└─ client/
   ├─ index.html        # только App для renderer
   └─ assets/           # карточки и их явные зависимости
```

Renderer не импортирует основной `App.vue`, его роутер или студию. Компоненты карточек
подключаются обычными импортами из модулей определений с произвольными именами.
Модуль может содержать default-экспорт и несколько именованных определений.
`CardSurface.vue` использует общий каталог
из `definitions.ts` и выбирает компонент по готовому `meta.definitionId`.
AST-плагин только обнаруживает экспорты и генерирует каталог; код определений
и их зависимостей собирается обычным Vite. Код загрузчиков
контекстов может входить в renderer-бандл, но renderer не создаёт resolver и не запускает
эти загрузчики: метаданные ему передаёт Bun или страница студии/debug.
Собственные запросы Vue-карточек выполняются через `useMetaReady`.
Отдельного реестра и ограничения на имя `.vue`-файла нет.
Общие парсеры и компоненты можно импортировать обычным `@/…`; `public/` сайта
в renderer не копируется, поэтому ресурсы карточек импортируются явно.

При серверной сборке Vite-конфиг вместо Vue-плагина подключает один load-hook,
который заменяет содержимое `.vue`-модулей на
`export default {}`. Backend нужен только `hasImage`, поэтому наличие импорта сохраняется,
а код карточек, их CSS, ресурсы и зависимости даже не загружаются в серверную сборку.
Браузерные сборки компилируют эти же импорты обычным Vue-плагином.

## Общий дизайн карточек

`shared/ui/meta/components/MetaCard.vue` задаёт общий фон, отступы, цвета, шапку и подвал.
Он используется внутри компонента конкретной карточки; `CardSurface` продолжает отвечать
только за выбор компонента, размеры и готовность. `MetaCard` не зависит от URL или данных.
Оба формата — Open Graph 1200×630 и X / Twitter 1200×600 — используют одну компоновку.

Четыре основных слота `MetaCard` независимо задают части карточки:

- `header` — шапка; по умолчанию бренд слева и необязательный `label` справа.
- `content` — содержимое в свободной области между шапкой и подвалом.
- `content-full` — отдельный слой на всю высоту карточки с сохранением горизонтальных
  отступов. Шапка и подвал отображаются поверх него.
- `footer` — подвал; prop `footer` слева и `footerRight` справа.

`footerRight` по умолчанию — `wotstat.info`; явно переданная пустая строка скрывает
правую подпись, сохраняя левую.

`content` и `content-full` могут использоваться одновременно: обычный контент остаётся
между шапкой и подвалом, а полноразмерный слой подходит для предметного изображения.
Внутренний `.content-body` каждого слоя служит контекстом позиционирования абсолютных
элементов его слота. Содержимое обоих слоёв центрируется по вертикали в своей области.

Если не объявлен ни один слот контента, карточка показывает большой `title` и `subtitle`
под ним. Prop `variant` выбирает область центрирования только этого готового блока:

- `full` (по умолчанию) — вся высота карточки, независимо от шапки, подвала и разделителей.
- `compact` — свободная область между шапкой и подвалом; если шапка убрана,
  между верхней гранью карточки и подвалом.

`variant` не влияет на явно переданные `content` и `content-full`, шапку или разделители.
Слоты `title` и `subtitle` меняют готовый блок, поэтому учитывают `variant`.
Карточки инфографики, заполняемые через props (бои, охват игроков, урон, карты,
результаты, стрельба, очки Чака и коробки), используют `full` по умолчанию.
`title` по умолчанию — WotStat Analytics.
Объявление любого слота контента, даже пустого, отключает готовый блок.
Default-слот не используется: своё содержимое нужно передавать в `content` или `content-full`.

Два boolean-props независимо включают разделители; оба по умолчанию выключены:

- `headerDivider` — линия под шапкой и внутренний отступ снизу 24 px.
- `footerDivider` — линия над подвалом и внутренний отступ сверху 24 px.

Явно пустой `<template #header />` убирает шапку, верхний отступ и промежутки;
`<template #footer />` убирает подвал и занимаемое им место. Разделители пустых частей
также не отображаются. Полноразмерный контент сохраняет центр относительно всей карточки.

Шапка задаётся props: `brand` по умолчанию — WotStat Analytics, необязательный
`specificBrand` добавляет перед ним название раздела основным цветом. Оба текста
полужирные, 24 px. Без `specificBrand` бренд использует основной цвет; с ним —
второстепенный `--meta-card-muted`. `label` выводится справа полужирным шрифтом 20 px.
Дополнительные слоты `brand`, `label`, `title` и `subtitle` позволяют заменить часть
готового содержимого. Слот `background` и prop `background` задают фон.

Debug-карточки передают содержимое в `content-full` и включают `headerDivider`.
Карточки техники используют `content` через `VehiclesMetaFrame`, с разделителем,
более плотной шапкой и без подвала. Общая обёртка Натиска `OnslaughtMetaFrame` включает
верхний разделитель, задаёт фон и состояния загрузки, ошибки и отсутствия данных;
boolean-prop `contentFull` выбирает, в какой слот передать содержимое специализации.

`GeneralMetaCard.vue` — обёртка над `MetaCard` для главного определения `default`:
пустой слот `header`, двухстрочный двухцветный WotStat / Analytics в слоте `title`,
подзаголовок «Статистика и аналитика танковых боёв» и футер «Мир танков · World of Tanks».
С `variant="compact"` заголовок с подзаголовком центрируется в доступной области над подвалом.
Этот же компонент используется
для общего превью фонов в студии; prop и слот `background` сохраняют выбор фона
и связанной палитры. Для обычных карточек с заголовком и подзаголовком используется
непосредственно `MetaCard`. Короткий `props.title` для изображения независим
от SEO-заголовка `meta.title`.

```vue
<MetaCard title="Бои" subtitle="Винрейт, время в бою и выживаемость" label="Инфографика" />

<MetaCard header-divider label="Статистика техники" footer="Статистика. Динамика. Сравнение.">
  <template #content-full>
    <VehicleComparison :vehicles />
  </template>
</MetaCard>

<MetaCard header-divider footer-divider specific-brand="НАТИСК" label="RU · Огненный сокол">
  <template #content>
    <OnslaughtStatistics />
  </template>
</MetaCard>
```

Каждый фон — отдельный Vue-компонент в `components/backgrounds/`. По умолчанию карточка
рендерит `AuroraMistBackground` — вариант 09 «Сияние: дымка»: тёмную основу с мягким
бирюзовым и лиловым светом. Чтобы заменить фон, передай компонент через prop
`background: Component` или одноимённый слот. Слот имеет приоритет над prop.

Дымка 09 использует одну PNG-текстуру 1200×630 в превью и серверном рендере, рассчитанную скриптом
`bun src/shared/ui/meta/components/assets/generateAuroraMist.ts`. Генератор лежит рядом
с PNG, запускается отдельно в Bun и исключён из проверки типов браузерного приложения.
Параметры цветов, размера пятен, размытия и яркости находятся в начале скрипта.
Смешивание и размытие выполняются в Float64;
перед единственным округлением до 8 бит добавляется монохромный треугольный дизеринг
с фиксированным seed. Результат сохраняется в `components/assets/aurora-mist.png`.
[Нативный вариант в Figma](https://www.figma.com/design/7rhi3UrkcnvFTGziK1XaJ1/wotstat?node-id=5614-799)
сохранён для сравнения; актуальная текстура не экспортируется из него.
Компонент выводит `<img>`, поэтому renderer дожидается декодирования текстуры;
выбранный паттерн накладывается отдельно, как у остальных фонов.

```vue
<script setup lang="ts">
import MetaCard from '@/shared/ui/meta/components/MetaCard.vue'
import ContoursBackground from '@/shared/ui/meta/components/backgrounds/ContoursBackground.vue'
import AuroraMistBackground from '@/shared/ui/meta/components/backgrounds/AuroraMistBackground.vue'
import customPattern from '@/shared/ui/meta/components/assets/contours.svg?url'
</script>

<template>
  <MetaCard :background="ContoursBackground" title="Статистика техники" />

  <MetaCard title="Статистика техники">
    <template #background><AuroraMistBackground pattern="dots" /></template>
  </MetaCard>

  <MetaCard title="Статистика техники">
    <template #background><AuroraMistBackground :pattern="customPattern" pattern-size="cover" /></template>
  </MetaCard>
</template>
```

Слот позволяет настроить props фона или добавить произвольную разметку и изображения.
Общая и сравнительная карточки также принимают `background` и пробрасывают слот.
`MetaCard` импортирует только фон по умолчанию; каталог всех компонентов с названиями,
описаниями и стабильным порядком номеров находится в `components/utils/backgrounds.ts`
и используется студией. Добавление фона не требует изменений в `MetaCard`.

`MetaCardBackground.vue` — общий абсолютный слой на всё полотно с псевдоэлементами
для света и текстур. Конкретные фоны используют его как основу и задают `palette`.
Для своего CSS-фона можно передать в слот `<MetaCardBackground palette="teal" style="background: …" />`.
`VehiclesBackground` повторяет фон страницы «Статистика техники».
Паттерн — отдельный слой `MetaCardPattern`, а не разновидность фона. Все фоны принимают
общие props из `MetaCardPatternProps`: `pattern?: string` и `patternSize?: string`.
`pattern` выбирает `dots`, `crosses`, `noise` или строку с URL / содержимым `<svg>…</svg>`.
Для импортированного SVG используй `?url`; `none` отключает наложение.
`patternSize` принимает CSS-размер, например `28px 28px`, `80px` или `cover`.
Точки и крестики повторяются в исходном размере, свой SVG по умолчанию центрируется
и масштабируется через `cover`; явно заданный размер позволяет повторять свой SVG плиткой.
Шум использует `soft-light` без маски, остальные паттерны плавно проявляются к правому краю.
У сияний, медной орбиты и графитового фона по умолчанию остаётся шум; у рельефа,
диагональных полос и сетки дополнительное наложение не задано.
Статические SVG-текстуры находятся в `components/assets/`. Зерно фиксировано, фоны не анимируются.

Цвета переопределяются CSS-переменными `--meta-card-text` и `--meta-card-muted` на компоненте,
отступы — `--meta-card-padding`, размер крупного заголовка — `--meta-card-title-size`.
Вторичный текст использует светлый ненасыщенный непрозрачный оттенок, близкий к белому
и подобранный к фону: оливковый для зелёного
рельефа, голубой для стальных фонов, лавандовый для сияния, бирюзовый для холодного рельефа
и тёплый медный для `EmberBackground`. `palette` базового `MetaCardBackground` выбирает
цвет из `metaCardSecondaryColors` в `components/utils/palette.ts` и через локальный
provide/inject сообщает его родительской карточке. Палитра меняется вместе с компонентом
фона, в том числе внутри слота; `--meta-card-muted`
по-прежнему позволяет задать свой цвет поверх выбранной палитры.
Для `VehiclesBackground` используется более приглушённый голубой `slate`, чтобы вторичный текст
не конкурировал с основным заголовком на почти однотонном тёмном фоне.
Общая, сравнительная и обе debug-карточки используют этот компонент;
запросы данных и `useMetaReady` остаются в специализациях.

## Определения и выбор по URL

### Виджеты

`pages/widgets/meta/` содержит общую текстовую карточку `/widgets` и один шаблон
для `/widgets/:widget*`. Определения находятся в `meta-definition.ts`, компонент
и согласование iframe — в `widgetMetaCard/`, общий каталог — в `utils/widgetCatalog.ts`.
Название и короткое
описание берутся из `widget-catalog.json`, автоматически собранного проектом
`widgets-collection` из тех же `define.widget.ts`, что использует каталог виджетов.
Контекст `widget-catalog` ждёт первоначальную загрузку до 3 секунд и обновляется раз
в 5 минут; при ошибке обновления сохраняется последний успешный снимок. Если снимка
ещё нет, HTML получает общий заголовок. Неизвестные маршруты и записи без превью
при загруженном каталоге показывают текстовую карточку.

Изображение использует `/iframe/widget-preview/:widget*` на сайте виджетов. Этот режим
выводит только `Preview.vue` с демонстрационными данными каталога и прозрачным фоном.
Он ждёт запросы данных, шрифты и изображения, затем сообщает `widget-preview-ready`
с названием и описанием. Перед готовностью и каждым ответом iframe дожидается
ненулевой геометрии: временный размер 0×0 при переключении видимости не отправляется
родителю. Ожидание идёт по кадрам без фиксированной задержки, в пределах общего
таймаута подготовки. Renderer через `useMetaReady` запрашивает
`widget-preview-measure` и получает `widget-preview-size` с `requestId`, `width`, `height`
и `insets: { top, right, bottom, left }` в пикселях. `width` и `height` описывают основной
блок виджета; `insets` — выступающие за него области `InsetsWrapper` с тенями и эффектами.
Замер использует реальные DOM-прямоугольники, учитывая отрицательные margins обёрток.
Пунктирные границы классических превью в этом режиме отключены.
Iframe отображается сразу во время подготовки: `opacity: 0` замедляет вызовы
`requestAnimationFrame` внутри него. Скриншот по-прежнему ожидает `useMetaReady`.
Карточка конкретного виджета не показывает надпись загрузки. В футере слева выводится
«Мир танков · World of Tanks», а правая подпись скрыта через `footerRight=""`.
Обе компоновки центрируются относительно всей карточки через слот `content-full`;
у области виджета есть вертикальные отступы по 48 px. Заголовок занимает всю ширину,
если он не помещается в одну строку левой колонки и основной блок виджета имеет
соотношение сторон не менее 1,5:1. Ширина текста измеряется с фактическим шрифтом
заголовка, без привязки к длине строки или конкретным виджетам. Короткие названия
и вертикальные виджеты сохраняют обычную компоновку с переносами заголовка.
Под широким заголовком описание и превью стоят в двух равных колонках и выровнены
по вертикальному центру. Заголовок находится на 32 px выше этой строки, высота которой
определяется описанием или превью. Вся широкая компоновка центрируется единым блоком
без учёта шапки и футера, без дополнительных отступов у превью.
Слот `content-full` остаётся тем же при смене компоновки, поэтому iframe не перемонтируется.
Начальный iframe — 640×400; после ответа его viewport расширяется на `insets`,
а корень внутри iframe получает такие же отступы, сохраняя ширину основного блока.
Масштаб для карточки рассчитывается по основному блоку. Расширенный iframe смещается
на `-left` и `-top` относительно этого блока, поэтому несимметричные эффекты не меняют
его центр и не обрезаются границами iframe. Согласование учитывает размеры и все четыре
отступа и заканчивается при расхождении не более 1 px или после пяти замеров.
Финальный `widget-preview-settle` / `widget-preview-settled` дожидается ресурсов
последней компоновки; после этого iframe вписывается в правую половину карточки.
CSS-анимации и переходы в этом режиме отключены. Ошибки передаются через
`widget-preview-error` и отклоняют подготовку изображения. Общий предел — 12 секунд;
размонтирование отменяет ожидание и снимает обработчики. Проверяются origin, окно
источника и идентификатор ответа.

`VITE_WIDGETS_URL` позволяет одновременно переключить каталог и iframe на локальный
проект: например, `VITE_WIDGETS_URL=http://localhost:5174 bun run dev --port 5175`.
Без override iframe учитывает поддомен ссылки (`ru.wotstat.info` →
`ru.widgets.wotstat.info`), а общий каталог использует `VITE_DEFAULT_URL_PREFIX`.
В production каталог скачивает Bun-контекст, поэтому ему не нужен CORS; iframe
общается с renderer через `postMessage`. Workflow `widgets-collection` устанавливает
кеш JSON на 5 минут и не меняет CORS бакета. В обычном браузере студия загружает
каталог самостоятельно и зависит от CORS сервера виджетов; локальный Vite-плагин
отдаёт разрешающий заголовок для JSON.

### Регистрация

Создайте `.ts`-файл с любым именем в любой вложенной директории `src/`.
Ручной регистрации нет: Vite-плагин разбирает TypeScript AST всех `.ts`-файлов
(кроме `.d.ts`) и находит экспортированные определения по вызову `defineMetaDefinition`,
импортированной непосредственно из `@/meta/utils` или относительным путём к этому модулю.
Импорт с переименованием (`defineMetaDefinition as defineMeta`) тоже поддерживается.
Существующие `meta-definition.ts` и `*-meta-definition.ts` продолжают работать без изменений.

В одном файле можно объявить несколько `export const name = defineMetaDefinition({ ... })`
и default-экспорт. Поддерживаются также локальные `const` с последующим
`export { name }`, `export { name as alias }` или `export default name`.
Если одно определение экспортировано под несколькими именами, в каталог оно попадёт один раз.
Вызовы должны быть на верхнем уровне модуля; вызовы внутри функций, изменяемые `let`,
обёртки-фабрики, namespace-импорты и цепочки реэкспортов не обнаруживаются.

В dev плагин отслеживает создание, изменение и удаление `.ts`-файлов, включая ещё
не импортированные приложением. При изменении модуля определения он инвалидирует
виртуальный каталог и перезагружает страницу; переименование обрабатывается как
удаление и создание. Изменения обычных модулей продолжают использовать штатный HMR Vite.
Обнаружение читает исходники без исполнения; импорт найденного экспорта исполняет
весь его модуль, поэтому модуль определения и его зависимости должны подходить
и для браузерной, и для серверной сборки.

```ts
import { defineMetaDefinition, everyHours } from '@/meta/utils'
import Card from './Card.vue'

export default defineMetaDefinition({
  id: 'player',
  component: Card,
  priority: 100,
  match: (url: URL) => url.pathname === '/player',
  meta: (url: URL) => ({
    title: `Статистика ${url.searchParams.get('nickname') ?? 'игрока'}`,
    description: 'Статистика игрока WotStat',
    imageAlt: 'Карточка игрока',
  }),
  revisionKey: () => everyHours(1),
  cache: { htmlSeconds: 10, imageSeconds: 3600 },
  name: 'Игрок',
  examples: [{ name: 'Пример', url: 'https://wotstat.info/player?nickname=Player' }],
})
```

`match` принимает точный pathname, `'*'` или синхронную функцию от полного URL.
Определения проверяются по убыванию `priority`. При равном приоритете порядок задан
по `id`, независимо от директории. Выбирается одно определение, без объединения
с менее приоритетными. Дубли `id` и отсутствие подходящего правила — ошибки.

`shared/ui/meta/generalMetaCard` — обычное определение: `id: 'default'`, `match: '*'`,
`priority: -1000`. Отдельной логики fallback нет; его можно переопределить теми же
правилами приоритета. `infographics-vehicles-compare` имеет приоритет 100 и матчится
на `/session/vehicles` (включая завершающий `/`) с непустым после `trim()` параметром
`compare`. Без `compare` используется `infographics-vehicles` с таблицей статистики.
У таблицы и сравнения по одной карточке. Экспериментальные варианты удалены;
прежний параметр `og-variant` игнорируется.

Стандартные страницы `/session` (бои), `/session/shots`, `/session/damage`,
`/session/results`, `/session/maps`, `/session/players`, `/session/lootbox`,
`/session/chuck-norris-tournament` имеют определения
`infographics-*` с приоритетом 10. Они используют `MetaCard` с разными
`props`, включая короткий заголовок, подзаголовок, подпись «Инфографика» и футер.
Завершающий `/` и query-параметры не меняют выбор этих определений.
Определения боёв, охвата игроков, урона, карт и результатов собраны в
`pages/infographics/pages/meta/definitions.ts` с именованными экспортами
`battleMeta`, `coverageMeta`, `damageMeta`, `mapsMeta` и `resultsMeta`.
Остальные определения лежат в `shots/meta/`, `lootbox/meta/`,
`chuck/meta/` и `vehicles/meta/`; специализированное сравнение техники
сохраняет более высокий приоритет.

`setupPageMeta(router, navigation.readyRoute)` автоматически выбирает определение из `definitions.ts` по
полному URL при каждом успешном переходе SPA, включая первый вход, изменения query
и возврат на страницу KeepAlive. Правила `match`, `priority` и порядок по `id` общие
с сервером и студией. Привязок `pageMeta` и импортов отдельных определений в роутере нет.
Хук обновляет title, description и keywords; отсутствующие description/keywords очищаются.
Стандартные страницы инфографики используют базовую мету, а страницы Натиска — реактивный `usePageMeta`.

SPA читает только `definition.meta`: объект или результат синхронной функции.
Каждый объявленный контекст передаётся как `undefined`, поэтому функция должна
обрабатывать отсутствие данных тем же fallback, что используется сервером до загрузки.
Например, Натиск берёт регион, сезон и ник из URL, а без списка сезонов показывает
«Текущий сезон»; название танка из debug-примера использует свой fallback.
В SPA не вычисляются `props`/`revisionKey`, не создаётся resolver и не запускаются
`load`, первоначальное ожидание или таймеры обновления контекстов.
Контексты по-прежнему загружаются сервером и отдельно при открытии Meta Studio.

В `src/routes.ts` `setupPageNavigation(router, queryStorage.readyRoute)` объединяет
готовность параметров и монтирование асинхронных страниц. `asyncPage` из
`pages/shared/asyncPage.ts` сохраняет `PageLoader` и сообщает о mount/activation
загруженного содержимого. Общий механизм находится в `shared/uiKit/pageNavigation/`.
Он проверяет готовность текущих route records, включая вложенные страницы и alias,
и не запускает загрузчики компонентов.

`queryStorage.readyRoute` становится доступным после естественной синхронизации
владельцев и query в роутере. Наблюдение не вызывает `history.flush()`, не снимает debounce
и не добавляет записей browser history. Пока параметры или асинхронная страница не готовы,
`navigation.readyRoute` равен `null`, а мета сохраняет существующие теги, включая
серверный title при первом открытии. После готовности базовая мета и локальные overrides
применяются вместе. Уход со страницы и опоздавший mount старого маршрута не делают
его мету активной. Одинаковые значения не записываются повторно; запросы статистики
страницы и отложенный ввод не входят в ожидание готовности. Необходимые метаданным
клиентские словари страница может явно включить в ожидание через `usePageMeta`.

### Клиентские переопределения

`usePageMeta` из `@/meta/pageMeta` вызывается в setup страницы и принимает объект,
ref или getter с необязательными `title`, `description`, `keywords`:

```ts
usePageMeta(() => ({
  title: player.value ? `${player.value.nickname} — статистика Натиска` : undefined,
}))
```

Getter и ref отслеживаются реактивно. `null` вместо объекта означает, что контекст
этого источника ещё загружается: менеджер сохраняет текущие title, description и keywords,
включая серверные при первом открытии. Базовая мета и другие overrides до готовности
всех активных источников также не записываются. После изменения getter/ref менеджер
повторяет обновление; деактивированный или ушедший маршрут не блокирует новую страницу.
`undefined` у отдельного поля наследует значение из Meta Definition
или активного родительского override; пустая строка явно очищает поле.
Хук регистрирует значения, а единственный менеджер применяет базовую мету и overrides
одновременно. Активны только владельцы текущих route records. Дочерний маршрут имеет
приоритет над родительским; для нескольких hooks одного уровня выигрывает последний
зарегистрированный для каждого заданного поля. Размонтирование удаляет источник;
KeepAlive-деактивация выключает его, активация возвращает.

Натиск использует `usePageMeta` с текущими refs региона, сезона и ника. Формат текстов
общий с серверными определениями (`onslaughtSelectionMetaTags`); ввод ника меняет title
до отложенной записи nickname в URL и не ждёт сетевых данных.
Главная, виджеты, Битва блогеров 2025 и debug-layout используют тот же `usePageMeta`
со статическим объектом. Это единственный API клиентского переопределения метаданных.
Переопределения относятся только к SPA: метаданные HTML и карточек на сервере
по-прежнему вычисляются из Meta Definition.

`meta` — объект или синхронная функция, возвращающая `title` и необязательные
`description`, `keywords`, `imageAlt`. Здесь разрешены быстрые вычисления из URL и контекста, но не сеть,
DOM или импорт browser-only модулей для вычисления метаданных. `cache` необязателен: по умолчанию HTML 10 с,
изображение 86400 с. `name`, `summary`, `examples` нужны только студии и тоже необязательны.

Debug-определения явно задают `htmlSeconds: 0`. Короткий TTL HTML позволяет быстро
получить новую сборку frontend и актуальный URL картинки; кеш картинки и `revisionKey`
настраиваются независимо.

`revisionKey` — необязательная строка или синхронная функция `(url, context) => string | undefined`.
Resolver вычисляет её при каждом разрешении метаданных с тем же URL и снимком контекста,
что и `meta`, и возвращает в `PageMeta.revisionKey`. Backend добавляет значение в параметр
`r` URL картинки для Open Graph и Twitter; при `undefined` параметр отсутствует.
Ключ может зависеть от URL, версии успешно загруженных данных или времени.
`everySeconds(seconds)` из `@/meta/utils` возвращает строку
`String(Math.floor(Date.now() / (seconds * 1000)))`: внутри периода ключ постоянный,
на границе меняется. Интервал должен быть конечным положительным числом секунд.
Для других единиц доступны `everyMinutes(minutes)`, `everyHours(hours)` и `everyDays(days)`:
например, `everyMinutes(15)`, `everyHours(2)` или `everyDays(1)`. Они переводят интервал
в секунды и используют тот же расчёт. День равен 24 часам; `everyDays(1)` меняет ключ
в полночь UTC. Базовая карточка использует `everyDays(1)`, debug-карточки — `everySeconds(1)`.
Вызывайте helper внутри callback (`revisionKey: () => everyHours(1)`), чтобы
значение не фиксировалось при импорте модуля. Этот ключ не меняет HTTP TTL и не запускает
обновление данных; `cache.imageSeconds` и загрузчики контекстов настраиваются отдельно.

`component` — необязательный Vue-компонент, импортированный из `.vue` обычным
`import Card from './Card.vue'`. Имя файла и расположение произвольные; работают
относительные пути и алиас `@/…`. Определения — обычные TypeScript-модули:
можно использовать константы, spread и функции.
Модули определений и контекстов не должны выполнять запросы, запускать таймеры
или другие побочные действия при импорте: загрузка выполняется только внутри `load`.
Импорт определения не запускает подготовку метаданных; её запускает создание resolver.
Импорт карточки служит для рендера; вычисление `match` и `meta` не должно обращаться
к внутренним свойствам Vue-компонента, поскольку для backend он заменяется пустым объектом.

`props` — необязательный объект или синхронная функция `(url, context) => object`.
Контекст имеет те же выведенные типы и снимок, что в `meta` и `revisionKey`.
Resolver вычисляет props и возвращает только результат в `PageMeta.props`.
Backend передаёт его в существующем `window.prepare({ url, format, meta })`,
а `CardSurface` разворачивает `meta.props` в обычные Vue props компонента.
Renderer и превью студии используют готовые значения, не вызывая функцию повторно
и не передавая загруженные серверные контексты в карточку.

Значения `MetaProps` ограничены JSON-данными: строки, числа, boolean, null, массивы
и вложенные объекты. Функции, Date, BigInt, Vue-компоненты и другие несериализуемые
значения нужно преобразовать до возврата из определения. Служебное имя `context`
зарезервировано для `RenderContext`: его нельзя задавать в props.
Существующие определения без `props` продолжают получать только `context`.

```ts
component: MetaCard,
props: {
  title: 'Урон',
  subtitle: 'Нанесённый и полученный урон в деталях',
  label: 'Инфографика',
  footer: 'Мир танков · World of Tanks',
},
```

Вместо объекта можно вычислить небольшой набор props из URL и общего серверного словаря:

```ts
props: (url, { vehicleNames }) => ({
  title: vehicleNames?.[url.searchParams.get('tag') ?? ''] ?? 'Техника',
  subtitle: 'Статистика танка',
}),
```

Для страницы без картинки достаточно такого определения:

```ts
import { defineMetaDefinition } from '@/meta/utils'

export default defineMetaDefinition({
  id: 'about',
  priority: 10,
  match: '/about',
  meta: { title: 'О WotStat Analytics' },
})
```

Такое правило не получает картинку или description из default. Студия показывает
текстовые метаданные и поле URL. Backend не добавляет image-теги, а запрос картинки
этой страницы возвращает 404 без обращения к Chromium.

## Карточки техники

В `pages/infographics/pages/vehicles/meta/definition/vehicles-meta-definition.ts` зарегистрированы
одна карточка таблицы и одна адаптивная карточка сравнения для
`/session/vehicles`. Все находятся в группе «Сравнение техники» студии.
Прежняя заглушка `vehicles-compare` удалена.

Оба определения вычисляют `title`, `description` и `imageAlt` синхронно общими функциями
`vehicles/meta/utils/tags.ts`. Таблица описывает выбранную категорию, группировку, нации,
регион, режим, период и выбранные показатели. Сравнение называет включённые источники и метрику;
одна линия получает «динамика», несколько — «сравнение». Различающиеся фильтры подписываются
у участников; у одного танка в разных условиях они выносятся после общего названия.
Классы техники в заголовках, описаниях и подписях всегда сокращаются: ТТ, СТ, ЛТ, ПТ-САУ, САУ.
Большие наборы сокращаются до нескольких участников с «и ещё N». Некорректная ссылка
или отсутствие включённых линий используют общий текст раздела.

Локальный контекст `vehicles-meta-catalog` объявлен в `vehicles/meta/utils/catalog.ts`.
Он загружает полные русские названия, теги и регионы актуальной/архивной техники и карт,
строит индексы компактных ID теми же чистыми функциями, что и браузерные компактеры.
Контекст обновляется раз в час, первое ожидание — до трёх секунд. Запросы ограничены
по времени, чтению и числу строк; превышение лимита не сохраняет частичный каталог.
Если имя хотя бы одного включённого танка ещё неизвестно, сравнение использует общий
текст раздела без технических тегов и ID. После загрузки имён появляются метаданные
участников. Категории уровней и типов не требуют словарей; неизвестные названия карт
заменяются нейтральной подписью «Выбранная карта».
Основная страница через `usePageMeta` использует те же функции и снимок уже загруженных
браузерных каталогов, поэтому названия сохраняются при навигации и изменении параметров.
Пока загружается нужный каталог, getter возвращает `null`, сохраняя серверные метаданные:
каталог танков нужен только для включённых танков сравнения, каталог карт — при выборе карт
в таблице или включённых источниках сравнения. Сравнение категорий без карт не ждёт словарей.
Ошибка загрузки завершает ожидание и применяет предусмотренный общий текст.

Карточка «Техника» показывает пять полных строк: боковая рамка таблицы продолжается до
нижнего края изображения. Экспериментальные варианты B/C и их настройки удалены.

Карточка `infographics-vehicles-compare` адаптируется к выбранным источникам.
Один или два включённых источника, каждый из которых
является конкретным танком, показываются крупными изображениями, названиями и цветными
значениями без легенды. Для одного танка график занимает левую часть содержимого на всю
высоту и продолжается вправо под силуэтом танка. Справа находится крупное изображение,
выходящее за край карточки, с названием и
значением над ним. Для двух танков график расположен сверху и продолжается под
приподнятыми изображениями; названия и значения выровнены снизу с отступом от края карточки.
`VS` появляется только для двух танков. Три и более источника,
любое сравнение уровней или типов, в том числе один уровень и смешанное сравнение
танка с категорией, используют большой график и легенду. Отдельные экспериментальные
варианты сравнения удалены.

Формат X / Twitter использует компактные отступы, а в дуэли — немного меньшие изображения
и высоту блока танков. Размеры текста сохраняются; разница высоты полотна распределяется
между контентом и графиком. Стили выбираются по `context.format` внутри карточки сравнения.

`utils/params.ts` читает только переданный URL общими декодерами параметров страницы,
без подключения к query storage или localStorage студии. Непустой `compare` выбирает
карточку сравнения; повреждённая ссылка получает явное состояние ошибки формата.
`table/useTableMeta.ts` использует существующие запросы и загрузчик таблицы, учитывает
группировку, период, поиск, локальные фильтры, пороги и сортировку. В изображении
показываются первые пять строк и не более четырёх показателей из выбранных пользователем
`columns`. Сначала резервируются показатели эффективной составной сортировки, остальные
места заполняются по существующему приоритету `defaultSlots`; агрегации наследуют приоритет
своего базового показателя. Не входящие в этот список метрики следуют порядку основной
таблицы. Итоговые колонки упорядочиваются общим `orderSlots`. Если сама сортировка содержит
более четырёх показателей, остаются её первые четыре ключа. Показатели всех ключей
загружаются для правильной сортировки строк, даже если часть колонок скрыта в карточке.
При одном-трёх выбранных показателях отображается только выбранный набор.
`MetaVehicleTable` — отдельная статичная разметка, основной компонент таблицы не используется.
Заголовки колонок используют Efficiency Icons; у агрегаций и производных метрик сохраняется
короткая подпись `slotHeadingLabel`, как в основной таблице. Десятичный
разделитель во всех числах карточек и на осях графика — точка. Пороги по боям/игрокам
применяются к данным, но не выводятся. Диапазон дат в заголовке, подписи дат отдельных
значений и нижняя строка о дневной статистике также не отображаются.
Показывается только первичная сортировка: короткая нейтральная полоска совпадает с
разделителем шапки и первой строки. При убывании к ней по центру приклеен направленный вниз
треугольник, при возрастании остаётся только полоска. Вторичные ключи и номера приоритетов
не отображаются; составная сортировка данных сохраняется. Иконки и подписи агрегаций
не сдвигаются из-за сортировки.
Сортировка по имени, уровню или типу отмечается под иконкой танка. Цвет значений и иконок
не меняется. Высота шапки таблицы — 68 px, размер иконок — 64 px.
Иконки числовых колонок центрируются над шириной
самого широкого видимого значения: скрытые копии чисел задают её через CSS Grid.
Режим боя и активные фильтры во всех композициях размещены справа от заголовка.
Актуальность техники в подписях не уточняется; выбранные уровни показываются римскими
числами без «ур.», типы и нации сохраняются. В таблице и её фильтрах только римские
числа уровней используют класс `mt-font`; остальной текст сохраняет шрифт карточки.
Перед обозначением типа в таблице и фильтрах показывается стандартная иконка `VehicleType`,
размер которой зависит от размера текста и сохраняет пропорции символов разных классов.

`compare/useCompareMeta.ts` декодирует бинарную ссылку существующим кодеком, разрешает
танки и карты через каталоги и загружает дневную историю существующим `useVehicleHistories`.
Учитываются включённость, цвета и собственные фильтры каждого источника, выбранная
метрика, пороги по боям/игрокам и известные неполные дни. Группировка по неделям/месяцам,
выбранное на странице окно сглаживания и интерактивные настройки в карточку не переносятся.
Сравнивать можно и танки, и категории. Общие режим и фильтры выводятся в заголовке,
регион в шапке объединяет регионы источников. Отличающиеся фильтры подписываются
под значениями танков в дуэли или под названиями в легенде панорамы; общий режим
боя в этих подписях не повторяется.

`compare/chart/MetaHistoryChart` — небольшой график непосредственно на `UniversalChart`:
линии, годовые метки и сетка, без `TimeSeries`, зума, тултипов и анимации.
Во всех вариантах графика всегда применяется AVG3 через общий `movingAveragePoints`:
усреднение трёх соседних точек внутри участков без пропусков, с сокращением окна на краях.
Масштаб Y рассчитывается по сглаженным точкам. Точность процентных подписей
оси соответствует шагу: `47%` при шаге 1, `47.5%` при шаге 0.5, `47.25%` при шаге 0.25.
Конечные нули убираются и при дробном шаге: `49%`, `49.5%`, `50%`.
Проценты рядом с танками в сравнении сохраняют два знака после точки. В таблице все
проценты показываются с одним знаком после точки, а дробные значения — максимум с двумя,
без конечных нулей: `1`, `1.5`, `1.25`.
Дистанция в таблице показывается целым числом с разделением тысяч, без суффикса «м».
Границы X всегда 6 марта 2024 — текущий момент, зафиксированный при монтировании.
Начальная дата общая с основной страницей (`defaultVehicleStatisticsFromDay`):
более ранние значения исключаются до построения линий и расчёта масштаба Y.
Данные, как на основной странице, включают только завершённые UTC-дни.
Недоступные дни и отфильтрованные значения исключены из данных и сглаживания. После AVG3
соседние доступные точки соединяются прямой через пропуски, без добавления новых значений.
`useMetaReady` ожидает данные и каталоги; ошибка загрузки отклоняет готовность renderer.
Ревизия меняется ежедневно, TTL изображения — час.

В каждом определении есть примеры для ручной проверки: танки/уровни/типы, разные регионы,
один/два/три танка, один уровень, смешанное сравнение, процентная метрика (в том числе
отдельный Объект 261), разные регионы и результаты боя, пустая и повреждённая ссылка.

## Карточки Натиска

У раздела `/onslaught` пять определений с приоритетом 100:

- `onslaught-general` — `/onslaught` и `/onslaught/general`: число игроков
  в собранных боях, количество боёв, игроков в Легенде и её порог.
- `onslaught-personal` — `/onslaught/personal` без ника: приглашение посмотреть
  свою статистику, с эмблемами рангов выбранной игры и сезона. Использует слот `content-full`:
  текст и эмблемы центрируются по всей высоте карточки.
- `onslaught-personal-player` — тот же адрес с непустым `nickname`: последний
  записанный рейтинг, ранг, бои, процент побед и средний урон. Показатели сопровождаются
  теми же иконками боёв, побед и урона, что и на странице личной статистики.
  При наличии данных использует слот `content`; без записей — отдельное состояние в `content-full`
  с ником, кратким пояснением и нейтральной иконкой боёв.
- `onslaught-leaderboard` — `/onslaught/leaderboard` без ника: порог Легенды,
  количество игроков в Легенде и топ-5 по очкам.
- `onslaught-leaderboard-player` — тот же адрес с ником: место, рейтинг и бои игрока.

Определения и Vue-карточки находятся в `meta/` рядом с `general`, `statistics`
и `leaderboard`; общая рамка и показатели — в `onslaught/meta/`, общие загрузчики,
разбор параметров и форматирование — в `onslaught/meta/utils/`.
Список регионов для страниц и карточек — в `onslaught/shared/utils/regions.ts`.
Во всех вариантах шапка показывает регион и название сезона. Фон — локальный
ресурс раздела, эмблемы — `RankIcon` с явными игрой и сезоном. Компоненты используют
`MetaCard` и одинаковую компоновку для 1200×630 и 1200×600.
Декоративные эмблемы общей и личной статистики и сводки лидерборда используют `fifth_hero` /
`sixth_hero`: максимальный доступный дивизион ранга, с общей эмблемой для сезонов без дивизионов.
Карточки конкретного игрока показывают его фактический ранг и дивизион.

`region`, `season`, `nickname` читаются из URL, без query storage и localStorage
посетителя. Отсутствующий или некорректный регион заменяется на RU, отсутствующий
или неизвестный сезон — на последний доступный в регионе, как в Settings раздела.
Список сезонов загружается общим серверным контекстом `onslaught-seasons` раз в час;
первоначальное ожидание — до трёх секунд. Названия берутся из словаря Comp7.
Renderer получает тот же список отдельным кешируемым запросом. Начало игрового дня,
длительность сезона и система рангов используют существующие доменные хелперы.

Общая статистика читается из `Comp7ArenasStatistics`: аудитория — `uniqMerge(players)`,
бои — `sum(battles)`. Аудитория — приблизительное число уникальных участников
собранных боёв, включая союзников и противников пользователей мода. Материализованное
представление `comp7_arenas_statistics_mv` собирает ненулевые `playersResults.bdid`
из `DeduplicatedBattleResults`. Это выборка записанных боёв, а не полная аудитория региона.
Лидерборд фиксируется на последнем доступном снимке `Comp7LeaderboardDailyByRank`
в пределах сезона с пятидневным запасом после конца, как на странице лидеров.
Сводка и строки топ-5 либо выбранного игрока возвращаются одним запросом и кешируются
единым ответом; QA-аккаунты исключены. Запрос группирует строки по дню и времени
пересчёта и выбирает последнюю группу. Отдельно кешировать время снимка и затем
запрашивать по нему игроков нельзя: `ReplacingMergeTree` заменяет строки при обновлении,
и прежнее время из кеша может уже отсутствовать в таблице.
Для выбранного игрока код дивизиона дочитывается из `Comp7LeaderboardByRank` по региону,
точному времени этого же снимка, месту и нику. Исходная таблица хранит историю пересчётов,
поэтому обновление дневной сводки не удаляет нужную строку. Код переводится общим
`getDivisionByLeaderboardCode`; при отсутствии строки или неизвестном коде сохраняется
расчёт по рейтингу и признаку Легенды. Буквы появляются только в сезонах, поддерживающих дивизионы.
Порог Легенды — минимальный рейтинг строк с `lastElite`, а не номер последнего места.
Поиск в лидерборде не зависит от регистра; личная статистика использует точный ник,
как основная страница, и фильтрует события по региону и периоду, бои — по `COMP7`.
Процент побед и средний урон считаются по полученным результатам; число боёв —
максимум количества начал и результатов. Ранг учитывает порог Легенды снимка.
В футере личной карточки игрока «Актуально на» показывает дату последнего события
рейтинга, начала или результата боя в выбранном сезоне (UTC); без данных дата не выводится.

SQL-строки экранируются, запросы ограничены по времени, чтению и количеству строк.
Статистика и картинка кешируются на 15 минут, `revisionKey` меняется с тем же интервалом.
Ошибки запросов отклоняют `useMetaReady`; отсутствие записей — самостоятельное
состояние карточки, без вымышленных показателей. Все варианты и примеры регионов,
сезонов и отсутствующего игрока доступны в студии `/meta`.

## Контексты определений

Общие контексты сайта объявляются в `src/shared/ui/meta/contexts/`. Специфичный контекст можно
объявить прямо в `contexts` определения; его `load` также может быть импортированной
функцией. Все загрузчики работают без Vue, DOM и browser-only импортов.

```ts
import { defineMetaDefinition } from '@/meta/utils'
import { vehicleNames } from '@/shared/ui/meta/contexts/vehicleNames'

export default defineMetaDefinition({
  id: 'vehicle-title',
  priority: 100,
  match: '/vehicle',
  contexts: { vehicleNames },
  meta: (url, { vehicleNames }) => {
    const tag = url.searchParams.get('tag') ?? ''
    return { title: vehicleNames?.[tag] || tag || 'Название танка' }
  },
})
```

Объявление контекста содержит обязательные `id`, `initialWaitMs`,
`refreshIntervalMs` и `load({ query, signal })`. Загрузчик получает обычный `query`
из `src/db/client.ts`, с теми же параметрами и результатом `{ data, ... }`, что и сайт:

```ts
const { data } = await query<Row>(sql, {
  abortSignal: signal,
  cache: { ttl: 3600 },
  proxyCache: true,
})
```

`proxyCache: true` включает общий Nginx-кеш группы `public`; доступен обычный формат
политики `cache` из `db/cache`, локальный кеш, очередь и отмена запросов.
Конкретные ограничения задаёт сам загрузчик через `settings` и `abortSignal`.
Например, `vehicleNames` ограничивает запрос восемью секундами, выполнение в ClickHouse —
пятью секундами; SQL ограничивает количество возвращаемых строк.

Ключ в `contexts` становится именем значения во втором аргументе `meta` и `revisionKey`.
`defineMetaDefinition` выводит его тип из результата `load` и добавляет `undefined`.
Это функция для вывода типов: она возвращает исходное определение без копирования
объекта или обёртки над `meta`. Все определения, включая статические и определения
без картинки, используют этот же хелпер.
Значения общие для процесса, не зависят от URL и используются как неизменяемые снимки.
Нужную запись по URL выбирает сам `meta`; полный словарь в HTML и Chromium не передаётся.

- Все объявления собираются автоматически из определений. Один и тот же объект
  контекста можно использовать несколько раз; разные объявления с одинаковым `id`
  останавливают инициализацию до запуска загрузок.
- При создании resolver запускается прогрев всех контекстов. HTTP-запрос ждёт только
  зависимости выбранного определения, параллельно. Срок `initialWaitMs` считается
  от начала первого прогрева и не продлевается новыми запросами.
- `initialWaitMs: 0` отключает ожидание. По истечении срока запрос получает `undefined`
  для ещё не загруженных значений; загрузка продолжает выполняться.
- После завершения загрузки следующее обновление запускается через `refreshIntervalMs`.
  Загрузки одного контекста не пересекаются. Ошибка записывается в лог и сохраняет
  последнее успешное значение; при первой ошибке остаётся `undefined`.
- Перед синхронным вызовом `meta` собирается объект текущих значений всех его контекстов.
  Обновления заменяют значения целиком. `resolver.close()` отменяет загрузки,
  освобождает ожидающие запросы и останавливает таймеры.

В Bun resolver создаётся один раз при запуске. В студии он создаётся при первом
обращении к метаданным и живёт до закрытия страницы; обновления реактивно меняют
title и предпросмотр. Студия использует `public`, Bun — настройки `internal-public`
из окружения. В браузере используется существующий `query` из `@/db`, без второго
клиента или кеша. Объявления контекстов не содержат адресов сервера или паролей.

## Студия

`/meta/backgrounds` — подбор фона: сохранённые варианты 05–07, 09, 12 и 15, сохранённые
сочетания дымки с точками (16) и крестиками (18), увеличенное превью выбранного.
В превью можно выбрать паттерн: по умолчанию, без паттерна, точки, крестики, шум или SVG
с линиями рельефа. Для фонов со своей геометрией (рельеф и диагональные полосы)
переключатель скрыт. Доступны примеры «Общая карточка» и «Статистика игрока»,
а также форматы Open Graph / X. Общий пример показывает настоящий `GeneralMetaCard`
с WotStat / Analytics и пустым слотом `header`. Пример статистики использует локальный
`StatisticsPreviewCard` на общем `MetaCard`: крупный заголовок слева и показатели справа.
Для него независимо переключаются контент на всю высоту, разделитель под шапкой
и разделитель над подвалом. Так область контента и линии можно проверить в любом сочетании.
Этот пример лежит рядом со страницей в `metaStudio/backgrounds/`, не входит в реестр
метаданных и не загружает данные.
Исходные номера явно заданы в каталоге и сохраняются при удалении вариантов из подборки.
09 — затемнённая дымка на основе 06, 12 — рельеф со свечением, 15 — исходный фон статистики техники.
Выбор на этой странице не меняет фон карточек сайта. `CardSurface` и `ScaledCard`
предоставляют default-слот для таких превью, сохраняя размеры, типографику и протокол готовности.
Для превью через слот достаточно передать `format`, без URL и метаданных страницы.

`/meta` — каталог определений, `/meta/cards/:id` — редактор. Оба экрана загружаются
асинхронно из основного SPA. Превью — те же Vue-компоненты через `CardSurface`, без iframe.
Карточки доступны в боковой навигации и адаптивной сетке превью с подписями снизу.
Карточки в обоих списках сгруппированы по части `name` до первого `/`, а оставшаяся
часть отображается как название карточки. Вложенных групп нет. Имена без `/`
попадают в «Другое». Группа «По умолчанию» идёт первой и содержит общую карточку,
Debug — последней. Названия и группы для студии готовит `metaStudio/utils/catalog.ts`.
Общая URL-форма
находится в `Studio.vue` над содержимым страницы и остаётся смонтированной при
переключении между каталогом и редактором. Поле занимает доступную ширину,
кнопка «Посмотреть» находится рядом с ним на всех размерах экрана.
По Enter или кнопке форма открывает редактор определения, выбранного общим resolver,
и передаёт введённую ссылку в режим «Свой URL». В редакторе ввод также обновляет
превью сразу. Выбор примера расположен в заголовке карточки; текстовые теги и TTL — рядом с полотном.
Можно вставить полный URL и увидеть реально выбранное определение. Вкладка «В сервисах»
показывает сразу четыре превью — Telegram, Discord, Slack и X / Twitter — в адаптивной
сетке. Каждое подписано названием сервиса, сохраняет его фон и показывает отправленную
ссылку над карточкой. Переключателя сервисов и пояснения о приблизительном виде нет.
URL, пример и формат сохраняются в localStorage между перезагрузками.
Выбор вкладки «Карточка / В сервисах» также сохраняется. Старое сохранённое значение
`render` восстанавливается как `card`. Вкладка «Карточка» через `RenderPreview`
встраивает тот же `meta/renderer/App.vue` с параметром `embedded`,
масштабирует его до доступной ширины и вызывает зарегистрированный им `window.prepare`.
Вызов запускается при открытии режима, изменении URL или формата и по кнопке
«Перезапустить». Кнопка находится под полотном, над журналом последних десяти вызовов,
который показывает время завершения,
длительность, фактический URL и ошибки. При смене URL или формата студия отменяет
текущую подготовку через `AbortSignal` и запускает вызов с актуальными параметрами,
не дожидаясь асинхронной карточки. Отменённый вызов не попадает в журнал.
Если HMR отменил незавершённую подготовку при пересоздании компонента, просмотр
автоматически повторяет вызов с актуальным кодом. После ошибочного вызова следующий
hot update также повторяет подготовку. Успешные вызовы при HMR не перезапускаются:
обычные обновления шаблона, стилей и состояния остаются в ведении Vue.
Замер включает общий код подготовки карточки, Vue, шрифты, изображения и кадры отрисовки;
скриншот Chromium в него не входит. Логика `prepare` одинакова в студии и backend.
`useStudioState` создаёт общее состояние оболочки студии и редактора через `createGlobalState`,
восстанавливает настройки и сохраняет их через `useLocalStorage`.
Передача URL между экранами работает и без localStorage; редактор меняет поля `cardState` напрямую.
`ScaledCard` использует `useElementSize` для масштаба превью.

Изменения компонентов обновляются через Vite HMR. Добавление, удаление или правка
Изменение файла определения обновляет каталог через стандартный механизм Vite, без собственного
watcher. При перезагрузке страницы введённый URL сохраняется. Страница студии закрыта от индексации так же, как debug.

Стили компонентов находятся в `<style scoped lang="scss">` с вложенностью по структуре
компонента. `CardSurface` задаёт базовую типографику полотна для совпадения студии и renderer.
Глобальные правила HTML renderer находятся в `src/meta/renderer/App.vue`,
в отдельном блоке `<style lang="scss">` без `scoped`, под классом `html.meta-renderer`.
Встроенный режим не включает этот класс, не меняет URL или прокрутку студии
и показывает `CardSurface` внутри собственного полотна без полноэкранного позиционирования.

## Backend и prepare

`createMetaResolver(query)` возвращает `readMeta`, `resolveMeta`, `warmup` и `close`.
`warmup()` ждёт первоначальную готовность всех контекстов: успешную загрузку,
ошибку с предусмотренным fallback или истечение `initialWaitMs`. Периодические
обновления продолжаются независимо от завершения прогрева.
Bun явно создаёт один экземпляр общего DB-клиента через экспортированный
`createDatabase(database)` и передаёт его `query` в этот resolver.
Студия и debug-страницы используют `getBrowserMetaResolver()` с существующим
браузерным `query`. Создание остаётся ленивым. Обновления контекстов вызывают
`triggerRef`, чтобы эти страницы пересчитали метаданные и передали их в `RenderPreview`.
Renderer не импортирует браузерный resolver и не запускает загрузку контекстов.
`readMeta(URL)` синхронно читает текущие снимки; `await resolveMeta(URL)` сначала
дожидается первоначальной готовности нужных контекстов в пределах их сроков.
Оба возвращают `definitionId`, `hasImage`, текстовые метаданные и `cache`.
`server.mjs` также экспортирует размеры форматов. Backend загружает артефакт один раз
при старте; отдельной версии протокола и внедряемых глобальных констант нет.

Браузерная точка входа состоит из `main.ts` и `App.vue`. Первый только монтирует `App`.
Компонент владеет полотном, текущим `context` и внешним `prepare` и напрямую
рендерит `CardSurface` с этим context. Vue Router в renderer не используется.
В `onMounted` App регистрирует `window.prepare` и инициализирует ресурсы renderer.
В `onUnmounted` удаляет свой обработчик, отменяет незавершённую подготовку
и снимает класс глобального reset. Метод доступен после монтирования.
Ожидание Vue, шрифтов, изображений и кадров остаётся в App; асинхронную подготовку
сама карточка регистрирует через `useMetaReady`.

Пул Chromium открывает `/render` отдельного App. Вызов
`window.prepare({ url, format: 'og', meta })` принимает уже рассчитанные метаданные
от Bun, студии или debug-страницы и монтирует карточку с `context: { url, format, meta }`.
`meta` обязательна и в `prepare`, и в props `RenderPreview`; fallback без метаданных нет.
`prepare` проверяет наличие
изображения у выбранного определения, очищает предыдущий context и дожидается
размонтирования перед установкой нового. Отдельные маршруты карточек и счётчик заданий не нужны.
Встроенная студия дополнительно передаёт `signal`; renderer объединяет его с сигналом
своего жизненного цикла. Отмена снимает текущий `CardSurface`, поэтому `useMetaReady`
прерывает таймеры и запросы старой карточки.
`Promise<void>` завершается после подготовки карточки, обновления Vue, шрифтов,
изображений и двух animation frame.
Backend задаёт размер viewport из `formats` и после `prepare` делает PNG или JPEG всей страницы
через `Bun.WebView.screenshot`. Формат задаёт endpoint: `/analytics/image.png` или
`/analytics/image.jpg`; оба доступны независимо от `IMAGE_FORMAT`. При обогащении HTML
backend выбирает ссылку и `og:image:type` по `IMAGE_FORMAT` (`png` или `jpeg`).
`IMAGE_QUALITY` задаёт качество JPEG от 0 до 100 и игнорируется для PNG.
В production и dev Docker Compose заданы `IMAGE_FORMAT: jpeg` и `IMAGE_QUALITY: '98'`;
это же значения по умолчанию при запуске без этих переменных.
Страница обслуживает одно задание за раз. `onErrorCaptured` перехватывает ошибки
дочерних Vue-компонентов; сбой карточки или загрузки изображения отклоняет `prepare`. Backend выбрасывает неисправную страницу из пула и создаёт новую.

Карточка без `useMetaReady` считается синхронной: ей не нужны событие готовности
или дополнительные настройки определения. Для асинхронной подготовки вызовите хук
в синхронном `setup` карточки:

```ts
import { useMetaReady } from '@/meta/cards/useMetaReady'

useMetaReady(async ({ signal }) => {
  data.value = await loadStatistics(props.context.url, { signal })
})
```

Callback запускается после монтирования. Он должен дождаться всей собственной работы,
включая асинхронную отрисовку графика, если она нужна. `CardSurface` через `provide/inject`
собирает Promise только своих экземпляров карточек и предоставляет `waitUntilReady()`.
App ждёт его, затем делает `nextTick` и обычную финальную подготовку изображения.
Ошибка callback отклоняет `prepare`. При размонтировании карточки её `signal` отменяется,
а ожидание отклоняется; используйте этот сигнал для отмены запросов и таймеров.
Хук работает и в обычных превью студии, где App отсутствует.

Карточка для URL `/debug/meta/delayed` и её определение лежат в
`src/pages/debug/pages/meta/cards/delayed/` и автоматически появляются в Meta Studio
как `debug-delayed` (`/meta/cards/debug-delayed`). На вкладке «Карточка» доступны App
и журнал `prepare`. Карточка показывает ожидание, через 5 секунд меняет текст на
«Карточка готова» и завершает хук. Метаданные по этому URL вычисляются синхронно;
задержка применяется только при рендере изображения. Кеш для этого определения выключен.

Внутренний Bun-сервер возвращает HTML renderer по `/render`, а отсутствующие assets дают 404.
Подготовка карточки не меняет адрес страницы. Параметр `embedded` управляет только
оформлением App; выбор карточки и ожидание готовности общие для обоих режимов.

## Nginx, кеш и обновления

Внешний Nginx раздаёт `/assets/` из общего каталога, а public-файлы — из `current`
(на диске эта ссылка указывает на `releases/<id>/dist`). HTML и
`og.wotstat.info/analytics/image.jpg` и `/analytics/image.png` направляются через внутренний gateway
на активный blue/green meta. В Bun и gateway нет отдельного кеша HTML и картинок.
Оба endpoint рендерят соответствующий формат без перенаправления между PNG и JPEG.
При переходе с PNG внешний конфиг `sites-available/og.wotstat.info` нужно применить вручную.

URL картинки содержит исходный путь, query, формат и версию `v` — общий ID
frontend-релиза из обязательного `dist-meta/release.json`. Он вычисляется при сборке
по всем файлам SPA и meta и используется также в dev. В production backend проверяет
его совпадение с ожидаемым `RELEASE_ID`. Необязательный параметр `r` содержит
`revisionKey` выбранного определения и меняется независимо от версии сборки.
Старые версии картинки перенаправляются на актуальную с сохранением расширения и `r`
и `Cache-Control: no-store`. `r` разделяет URL для кеша, но не выбирает исторический
снимок данных: сервер рендерит текущее содержимое. Новый URL изображения станет
известен внешнему сервису, когда тот повторно прочитает метаданные страницы;
уже сохранённые превью не обязаны обновляться по этому расписанию.

HTML имеет `max-age` из определения, ограниченный backend сверху 300 секундами.
Ни Nginx, ни CDN не должны увеличивать этот срок или бессрочно выдавать stale HTML:
эта граница включена в срок хранения assets. Если gateway недоступен, внешний
Nginx возвращает локальный актуальный `index.html` с `200` и `no-store`.
Для картинок разрешён stale cache при ошибке upstream; при MISS возвращается ошибка изображения.
Отсутствующие assets по-прежнему дают 404, а не HTML.

Каждый процесс монтирует конкретный неизменяемый `dist-meta` релиза. Новый процесс
создаёт собственные контексты и Chromium; `/ready` подтверждает прогрев всего пула
и первоначальное ожидание контекстов. После готовности кандидата переключается gateway.
Старый процесс продолжает
завершать запросы до ухода старых workers gateway, после чего останавливается.
При SIGTERM Bun сначала закрывает вход для новых соединений и дожидается принятых
запросов, затем освобождает resolver и Chromium. Общий предел завершения — 30 секунд.

Все контексты пересоздаются; значения не переносятся по id между версиями.
Resolver обязан экспортировать `warmup`; без него новый meta-процесс не запустится.

`dist`, `dist-meta` и манифест публикуются одной версией. Активная, предыдущая для
отката и ещё не истёкшие версии сохраняются; общие assets удаляются по ссылкам из
манифестов, а не по mtime. Подробнее — [деплой](01-overview.md#деплой).
